# Connect Jira

Status: draft
Roadmap: Phase 1 — Foundation

## Assumptions

Correct these now, or the work goes ahead on them.

- **Jira Cloud only.** You connect with a site address, the email you sign in with and a personal API token, as the product spec says. DevHub sends them as HTTP Basic auth and checks them with `GET /rest/api/3/myself`. Jira Server, Data Center and OAuth are out of scope.
- **The library is `jira.js`.** `docs/architecture.md` lists it as planned for this spec. It goes into `@devhub/core` only, through `pnpm add`. Version 6 depends only on zod. Its only caller is `packages/core/src/integrations/jira/client.ts`. `msw` joins core's dev dependencies, so tests can fake Jira's API; MSW is already part of the decided stack.
- **The site and email are kept in `<DEVHUB_HOME>/settings.json`**, with mode 600, never in the keychain and never in `.env`. The file is written to a temporary file and then renamed, so a crash can't leave half a file. It never holds a token. Spec 005 adds its own settings to the same file. Core gets the folder from the host, the same way `apps/server` already passes it for `runtime.json`.
- **Connect checks first, then saves.** DevHub asks Jira whether it accepts the email and token. It saves the site, the email and the token only when Jira says yes. On any failure nothing changes, and an existing connection stays exactly as it was.
- **"Connected" means Jira accepted the token**, not just that one is saved. The status check asks Jira at most once every 2 minutes, and requests that arrive together share one check. It waits at most 10 seconds for Jira. Nothing polls in the background. Spec 007's 2-minute refresh will keep it current.
- **Status reads the keychain only once a site and email are saved.** A fresh DevHub, CI and the e2e run never touch it.
- **The site field forgives.** It accepts `your-team`, `your-team.atlassian.net` or any `https://your-team.atlassian.net/…` link, and keeps `your-team.atlassian.net`. Spaces at the start or end of any field are trimmed, because a pasted token often carries one. A token still follows the rule from 002: no spaces or line breaks inside, and at most 4096 characters.
- **New endpoints:**
  - `GET /api/jira/connection` returns the saved site and email, and whether `.env` holds a Jira token the fallback can use. It never reads the keychain.
  - `PUT /api/jira/connection` checks and then saves.
  - `DELETE /api/jira/connection` disconnects.
  - Two new error codes, which GitHub (spec 004) will reuse. Jira refused the email and token: `integration_rejected` (422). There's no Jira at that address, or the network, a timeout or a Jira error got in the way: `integration_unreachable` (502). The form puts a rejected answer under API token and an unreachable one under Jira site.
- **The token stays inside `client.ts`.** That file alone builds the Basic auth header. An error from jira.js becomes an error of ours with a fixed message, so its headers never travel further. As a second guard, the logger redacts every `authorization` header. Both were promised to 003 in spec 002's review.
- **The e2e run gets its own keychain.** A new setting, `DEVHUB_KEYCHAIN=os|memory` (default `os`), lets Playwright start the server with an in-memory keychain. The e2e run can then never read your real "DevHub" item. This too was promised to 003.
- **DevHub trusts the certificates your computer trusts.** The server starts with Node's `--use-system-ca`, so a company TLS proxy works without extra setup. Without it, calls to Jira from a corporate laptop fail with a certificate error.
- **After Connect succeeds**, the form closes, focus returns to the row's Manage button, and a polite status message says "Jira is connected."

## Goal

I connect Jira once from Settings with my site, email and an API token. DevHub checks them with Jira before keeping anything, puts the token in my keychain, and the Jira row says in words whether the connection works. When it doesn't, the row says why and what to do.

## Out of scope

- Reading your assigned issues and the current sprint (Q1 moves them to specs 007 and 008), and the SQLite cache.
- Creating a Jira issue (spec 008).
- Jira Server, Data Center, custom domains, OAuth, and more than one Jira site.
- Showing your Jira name in the sidebar footer.
- Choosing which Jira field holds acceptance criteria (the product spec's open question; it belongs with the brief in spec 011).
- GitHub (spec 004) and Slack (spec 016).
- Changing the Settings callout when tokens come from `.env` (spec 005, from spec 002 Q6), and the other Settings tabs (spec 005).
- Checking Jira in the background on a timer (spec 007).
