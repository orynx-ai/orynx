## Assumptions

Correct these now, or the work goes ahead on them.

- **One new host, `apps/desktop`, and nothing in the screens changes.** Electron's main process starts the built `apps/server` bundle in a `utilityProcess` with `--serve-web`, and the window loads `http://127.0.0.1:<port>` on the port the hub got (Q2). The window runs `apps/web`'s build as it is: same token meta tag, same Host check, `Platform.kind` stays `'web'` (no code reads it). `apps/desktop` imports no `@devhub/*` package; it starts the server by its path. The boundaries gate and `docs/architecture.md` learn the new host (new-package skill).
- **The packed app keeps the layout `main.ts` expects.** The server bundle, its `package.json`, its production `node_modules` (made with `pnpm deploy --legacy --prod` and a hoisted layout) and `apps/web/dist` sit as plain files in the app's resources folder, outside `app.asar`: `server/dist/main.mjs` finds `../../web/dist` and `../package.json` as it does today. The repo `.env` isn't there, which `readEnvFile` already treats as no file. Plain files also let better-sqlite3's `.node` file and Claude Code run.
- **Electron's Node.** /plan pins the newest stable Electron whose `process.versions.node` meets the repo's `engines` (24.15 or later), for `setDefaultCACertificates` and the rest. If none does, /plan stops and asks. better-sqlite3 13 and `@napi-rs/keyring` are both Node-API, with prebuilt files for each platform, so they load in Electron as built (checked in task 9; no rebuild, so Q7 wasn't needed).
- **Claude Code keeps Anthropic's signature.** The bundled `claude-agent-sdk-darwin-arm64/claude` (268 MB, team `Q6L2SF6YDW`, hardened runtime with JIT entitlements) is left out of signing (`signIgnore`), so its signature and entitlements stay as Anthropic made them. The rest of the macOS app is ad-hoc signed (`identity: '-'`), because Apple Silicon won't run an app with no signature at all.
- **PATH from the login shell.** An app opened from Finder gets `/usr/bin:/bin:/usr/sbin:/sbin`. At start the main process asks the user's login shell (`$SHELL -ilc`, 10-second limit: a real zsh with nvm took 0.8 s warm and over 5 s on its first start after login) for its `PATH` and gives the server the PATH it was started with, followed by every login-shell entry not already in it. That keeps a PATH the e2e run sets (fake `gh` first) and adds Homebrew's folders for `gh`, `node` and `pnpm`. If the shell fails or is slow, the server gets the PATH it was started with and the log says so. Only `apps/desktop/src/config.ts` reads `process.env` (rule 9).
- **A free port each launch, one copy** (Q2). The app starts its hub with `DEVHUB_PORT=0`, so the OS picks a free port and a taken port never stops Orynx. `config.ts` accepts 0, and the server writes the port it got, not the one it asked for, to `runtime.json` and its log line. The main process reads the port from `runtime.json` once that file names the server's own pid. The page's address changes each launch, so what the page saves in the browser (theme, sidebar width, Tickets view, the composer's model and effort) starts fresh each time: the user accepted that on 2026-10-19. `DEVHUB_HOME` still works as for `pnpm start`. A second launch focuses the open window (single-instance lock).
- **Same home as `pnpm start`, one hub per home.** The app uses `~/.devhub` and the keychain service "DevHub", so settings, sessions, worktrees and connections carry over from the terminal version. Before it starts its hub, the app reads `runtime.json`. If that file names a process that is still running (another Orynx on this home, such as `pnpm start` or `pnpm dev`), the app starts nothing and shows Q2's dialog: two hubs on one home would overwrite each other's `runtime.json`, settings and sessions. A `runtime.json` left by a process that has ended is ignored. Your own `pnpm dev` runs beside the app with its own `DEVHUB_HOME` and `DEVHUB_PORT`, as parallel sessions already do.
- **The window.** One window, 1280 × 800, at least 360 wide, titled Orynx. It shows only once the page has drawn, so nothing flashes white in dark mode. It isn't remembered between launches. `contextIsolation` and `sandbox` on, `nodeIntegration` off, no preload script. Electron's default menu stays, so ⌘C, ⌘V, ⌘Z and ⌘R work and About Orynx shows the version.
- **Links.** A new window (`window.open`, `target="_blank"`) for an `https:` address opens in the default browser and the Orynx window stays where it is. Moving the Orynx window to a `vscode:` or `cursor:` address (Open in) hands it to the OS. Every other navigation away from the hub's own address and every other new window is refused.
- **Closing and quitting.** On macOS, closing the window keeps Orynx in the Dock with the hub running; clicking the Dock icon opens a window on Home. On Linux, closing the window quits. Quitting stops the hub and its sessions the way Ctrl-C stops `pnpm start` today, and removes `runtime.json`. It doesn't ask first.
- **The log.** The server's output goes to `<DEVHUB_HOME>/logs/orynx.log` (folder 0700, file 0600), replaced at each launch, with the previous launch's kept as `orynx.old.log`. The server already never logs a token.
- **Waiting for the hub.** The main process opens the window when `runtime.json` names the server's pid and `GET /` on its port answers, checked every 200 ms. If it hasn't answered in 30 seconds, or the server process exits, Q3's dialog shows.
- **Update checks.** electron-updater asks this repo's GitHub Releases at launch and every 6 hours, with no token and no other data. While the repo is private the answer is 404: nothing shows, and the log says "Orynx couldn't check for updates (404)." Once the repo is public the same build starts finding updates, with no change.
- **macOS can't install updates (unsigned).** It only tells you (Q1) and links to the latest release page. Linux's AppImage downloads the update in the background, checks its sha512 against `latest-linux.yml`, and installs it when you quit. Orynx never restarts itself, so a running session is never cut off by an update.
- **The notice shows once per launch** for a newer version, in a native dialog. Nothing about it is saved, and the page doesn't change.
- **Versions.** `apps/desktop/package.json` holds `0.1.0`. The release job writes `0.1.<run number>` into `apps/desktop/package.json` and `apps/server/package.json` before it builds (so About Orynx, the file names and `/api/status` agree) and commits nothing. Changing `0.1` to `0.2` on `main` starts `0.2.<run number>`. Re-running a run that already published fails without touching its release.
- **`settings.json` survives an update that can't read it.** Today `settings-store.ts` reads a file that fails the schema as `{}`, and the next save writes over it. Now the save first renames the unreadable file to `settings-<YYYYMMDD-HHmmss>.unreadable.json` (0600) beside it, then writes the new one. The log says "<path> is not valid; Orynx keeps it beside the new one when settings next save." when it reads the file, and "Orynx kept the settings it couldn't read as <kept path>." when it saves. The cache (`cache.db` is made again when it can't be read), the session store (an unreadable session stays on disk, out of the list) and the browser's saved preferences (zustand `persist` with `version` and `migrate`) already survive a change of format.
- **The release workflow** (`.github/workflows/release.yml`, on push to `release`, one run at a time, none cancelled) uses only `GITHUB_TOKEN` with `contents: write`, and no other secrets. `ci.yml` keeps running on pull requests and `main` as today. The release workflow:
  1. Fails at once if the pushed commit isn't on `origin/main`.
  2. Runs `ci.yml`'s jobs (through `workflow_call`).
  3. Builds macOS arm64 on a macOS runner and Linux x64 on Ubuntu, in parallel.
  4. Publishes one GitHub Release `v<version>` (not a draft, not a prerelease) with notes GitHub writes from the commits.
- **Pushing to `release`.** `git push origin main:release` runs the pre-push hook as on `main`, so the review stamp isn't asked for. On GitHub you turn on "no force pushes" and "no deletion" for `release` yourself; this branch tells you how and changes no repo settings.
- **New dependencies** (Q6): `electron`, `electron-builder` and `electron-updater`, in `apps/desktop` only. electron-vite isn't used. `docs/architecture.md`'s stack table and its "Porting to a desktop app" section change to match (a utilityProcess on the port the OS picks, in place of `createServer()` in the main process with hash history).
- **Tests never reach the real things.** A Playwright test launches the built (not packed) app with `_electron.launch`, a temporary `DEVHUB_HOME`, `DEVHUB_KEYCHAIN=memory`, the e2e run's fake Claude Code and a fake GitHub Releases server, on Linux under `xvfb-run` in CI. `shell.openExternal` is replaced by a recorder in that test only, as an outside service. Unit tests cover the PATH merge, the link rules, the one-hub-per-home check, the port written to `runtime.json`, the version stamp and the settings rename. Gatekeeper, the keychain prompt and a real sandboxed command are checked by hand on a Mac, once per release of this spec.
- **Docs.** A new `learn/desktop-app.md` covers how the app starts the hub, how `release` publishes, and how to make the repo public later. CLAUDE.md's Layout and Workflow lines name `apps/desktop` and the `release` branch. `docs/product/spec.md` ("started with `npm install && npm start`") is yours: the branch hands you a script for its change, as 015 and 022 did.

## Goal

I install Orynx like any other app, open it from the Dock or the app menu, and it just works: my Jira, GitHub and Claude connections, my folders and my sessions are all there, with no terminal and no Node to install. When I push `main` to `release`, CI builds the app and publishes it, and the apps already installed find the new version: Linux installs it on its own, and the Mac tells me to download it.

## Out of scope

- Signing and notarizing for macOS, installing updates on a Mac, Intel Macs, Windows and the Mac App Store.
- A desktop `Platform` (native file dialogs through a preload, notifications), and any change to `@devhub/app`, `@devhub/ui`, `@devhub/api-client` or `@devhub/contracts`.
- An update banner inside the page, a Check for Updates menu item, release notes in the app, a beta channel and staged rollouts.
- Opening at login, a tray or menu bar icon, remembering the window's size and place, more than one window.
- Showing the server's start-up warnings (sandbox missing, cache reset) in the window. They stay in the log.
- Homebrew, apt or Snap packages, crash reports and usage data.
- Docker, and a login service with the page installed as a browser app: both weighed on 2026-10-19, and the user kept the native app.
- Running the app beside `pnpm dev` or `pnpm start` on the same home (AC-8).
- Keeping the page's saved preferences across launches (Q2).
- Making the repo public and the GitHub branch protection for `release`: you do these on GitHub.

## Design

`none` — the window shows the existing screens unchanged. The only new things you see are the OS's own dialogs (Q1–Q3, in the system's own style and theme) and the app icon (Q4).
