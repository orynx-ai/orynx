# Answer from anywhere, review comments, standup, read ahead and spend

Status: approved, every question answered (9 Nov 2026)
Roadmap: not on the roadmap. On 9 Nov 2026 the user picked all five items from a list of next features and asked for them as "add all these in single feature and single pr". 057 is the next free number. `origin/main` ends at 052, and 053–056 belong to other sessions' branches and worktrees (colour themes, custom agents, the demo, the settings revamp).

## Assumptions

Correct these now, or the work goes ahead on them.

**Across the five parts**

- **One spec, one branch, one pull request**, as the user asked. The plan orders tasks part by part (A to E), one commit per task. That way each part can be reviewed, and reverted if needed, on its own.
- **No new dependency.** Electron's own `Notification`, `@slack/web-api` and Discord's REST API, already in use, cover it all.
- **056 (settings revamp) is in progress in another worktree** and changes Settings. This spec adds three Settings rows and one connection field. Whichever branch merges second rebases.

**A. Answer Claude's questions without opening Orynx**

- **Only Claude's questions (spec 051) can be answered from outside Orynx.** An approval (command, edit, push, pull request, Jira change) sends a ping that says Claude is waiting. The ping never carries the command, and the approval can't be allowed or denied from outside Orynx (rule 11, spec 029 Q3). See Q1.
- **Off by default.** A new row in Settings › Notifications turns it on and picks Slack, Discord, or both. It sends the question's text and choices to that service. For anyone who turns the row on, this undoes spec 051's rule that the question's text stays on the laptop.
- **Only a call with one question can be answered from outside.** For a call with 2 to 4 questions, the message says to answer in Orynx, and replies aren't read.
- **The message** has the ticket and the session's title, the question, and the choices numbered 1–4 with their descriptions. It ends with how to reply. Claude Code's own "Other" isn't numbered, because any text you type is the Other answer.
- **Your reply:**
  - Reply to the message: in its thread on Slack, or with Reply on Discord. On Discord, a plain message also counts when only one question is waiting.
  - Orynx reads only replies from your saved Slack or Discord user ID, and takes only the first one.
  - A number picks that choice, and "1, 3" picks several when the question allows several. "skip" skips (Claude gets spec 051's skip line). Any other text is the Other answer, up to 2,000 characters.
  - A number out of range, or several numbers on a one-pick question, gets a reply asking again. The question keeps waiting.
- **Whichever answer comes first wins, wherever it was given** (spec 051 AC-9).
  - Once Orynx takes a chat reply, it replies "Sent to Claude.".
  - If you answer in Orynx first, or the session stops, Orynx replies in the thread so you know. A reply sent after that is ignored.
  - These short replies are the only extra messages Orynx writes.
- **Orynx checks for your reply every 15 seconds while a question it sent is waiting, even with no Orynx page open.** Today the inbox syncs only while a page is open. Checking stops once the question is answered or skipped, or the session stops.
- **Discord**: the bot that's already connected DMs your saved Discord user ID and reads its own DM with you through REST, with no gateway.
- **Slack**: Slack doesn't notify you about a message your own token posts, so a DM through the user token would arrive without a notification. Slack therefore needs a bot. Settings › Connections › Slack gets an optional bot token (`xoxb-`, scopes `chat:write`, `im:write`, `im:history`). It goes in the keychain and is checked with `auth.test` before it's saved. See Q2.
- **Desktop notification**: in the desktop app on macOS, the question's notification gets a reply box. Typing in it works the same as a chat reply. The notification shows the question and its choices only when the Settings row is on. In the browser and the installed PWA, a click still opens the session at the question; those would need a service worker, which spec 040 chose not to have. See Q3.
- **The answer step says where the answer came from**: "You answered from Slack", "from Discord" or "from a notification".

**B. Review comments in the diff** (spec 048, part G)

- **A session with its own pull request open gets a Review comments tab beside Changes**, with the number of unresolved threads, as `session-review.html` draws it. That covers a PR from spec 014 and a Build on your own PR from spec 031. Review sessions on someone else's PR (spec 050) don't get the tab.
- **Threads are read from GitHub when the tab or Changes opens, and again after each inbox sync that sees the pull request change. They aren't stored** in `session.json`. Spec 048 expected them to be stored, but reading them live leaves nothing to keep up to date.
- **Each thread gets three more fields**: the side it's on (`diffSide`), `isOutdated`, and when its last comment was written. Resolved threads stay hidden, as in spec 049. The limits stay spec 049's: 50 threads, 20 comments each. The tab shows every comment, not only the last.
- **A thread shows inside the diff only when its file and line land on a line the Changes diff draws, on the same side, and nothing in that file has changed since the last push.** Otherwise the line numbers could be wrong. Every thread is in the tab. One that can't be placed in the diff is marked "Outdated" (GitHub says so) or "Not in this session's changes".
- **The file list's comment count (spec 050) counts reviewers' threads too.**
- **Notes reuse `DiffNote`**: the author, the time, the comments as Markdown, and Open on GitHub. Spec 049's Reply to reviewers stays in the next-move bar.

**C. Standup draft**

- **This corrects the list from earlier, which said nothing new needs fetching. Two new reads are needed.** Orynx's own records hold your sessions, the pull requests opened through Orynx, pushes, posted reviews and the Jira moves Claude made. They don't hold pull requests merged on GitHub, or tickets you moved in Jira yourself. So the standup adds one GitHub search (`is:pr author:@me merged:>=<day>`) and one Jira search (`status CHANGED BY currentUser() DURING (<day>, <day+1>)`).
- **"Yesterday" means the last working day**, so Friday on a Monday. It runs from midnight to midnight in the laptop's time zone.
- **Orynx fills in a template; Claude doesn't write it.** That's free, quick and the same every time. See Q5.
- **The draft has three parts**:
  - **Yesterday**: merged, opened and reviewed pull requests, Jira moves, and sessions that finished without a PR.
  - **Today**: your Jira tickets in progress in the current sprint, and sessions that are waiting on you.
  - **Blockers**: "None", for you to change.
  - It uses `•` bullets in plain text, so it pastes cleanly into Slack and Discord.
- **Home's quick starts get a third chip, "Write my standup".** It opens a dialog with the draft in a box you can edit, plus Copy and Close. You paste it yourself; Orynx posts nothing. See Q4.

**D. Review requests read ahead**

- **Off by default.** A new row in Settings › Coding agent turns it on.
- **When it's on, every review request that arrives afterwards starts a spec 050 review session in the background**, as if you'd pressed Review on Home's row. Requests that were already waiting aren't read.
- **Limits**: one read ahead runs at a time. None starts while 2 or more sessions are working, so one of the 3 session slots stays free for you. At most 5 run in a day. A request that has to wait starts when a slot frees, oldest first. Anything left over at the end of the day waits for the next one. See Q6.
- **It watches the inbox's sync**, so it only notices new requests while Orynx is open in a tab or in the desktop app.
- **It never posts.** Home's row shows "Claude is reading", then "Draft ready". Review opens that session (spec 050 keeps one session per PR). Posting stays spec 050's dialog and your click. The existing "Session finished" notification tells you a draft is ready, so there's no new notification.
- **A request withdrawn before its turn is dropped. One that's already running finishes.** Turning the row off drops the queue the same way.

**E. Spend and limit warnings**

- **Each row on the Sessions page shows the session's cost, "≈ $1.42"**, the same figure spec 047 shows on the Session screen. Codex sessions, and sessions with no cost, show nothing.
- **Three tiles above the list: Today, This week, This month.** Each shows "≈ $X" and "N sessions". A session's whole cost counts on the day it started. The tiles count every session, whatever the filters.
- **A cost never goes down.** The SDK can send a total of 0 after a crash. Orynx keeps the larger of the saved total and the new one, which settles spec 047's `shortcut:`.
- **Orynx's calls that have no tools aren't counted**: the quick read, the pull request draft and the commit message. They're small.
- **Limit warning**:
  - While a session runs, Claude Code sends a rate-limit event. When it says you're close (`allowed_warning`), a warning callout appears at the top of Home and of the Sessions page, with how much is used and when it resets.
  - You also get one notification (bell, pop-up, desktop) for each limit window, under the existing "Session hit a limit" row in Settings › Notifications.
  - The warning goes when the reset time passes, or when a later event says `allowed`.
  - Orynx only knows what its own sessions heard. It doesn't use the SDK's unstable `usage_EXPERIMENTAL_…` call.

## Goal

When Claude asks me something and I'm not at my desk, I want to answer from Slack, Discord or the notification instead of finding the session stuck. In my own pull request, reviewers' comments should sit right next to the code they're about. I want my standup written for me from what I actually did, and a review request to arrive with Claude's draft review already waiting. And I want to see what my sessions cost, and be warned before I hit my Claude limit, not after.

## Out of scope

- Allowing or denying an approval from Slack, Discord or a notification (Q1).
- Answering a call with more than one question from outside Orynx.
- Answering from the browser's or the PWA's notification, a service worker, and reply boxes on Windows or Linux.
- Email, SMS and phone push.
- Discord DMs as Home items, and the Slack bot reading anything except its own DMs with you.
- Replying to or fixing a single thread from its note, resolving threads in Orynx, writing new comments, and threads on other people's pull requests.
- Storing review threads.
- Posting the standup to Slack or Discord (Q4), scheduling it, Claude writing it (Q5), and team standups.
- Reading ahead requests that were already waiting, other kinds of PR, re-reading after new commits, and posting without a press.
- Budgets, stopping a session on cost, cost per step, the cost of calls that have no tools, Codex cost, charts and export.
