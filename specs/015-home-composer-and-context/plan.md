## Order of work

Today a session starts only from a ticket, through Ship. This spec adds a second way in: your words, a folder, and the chips you add, all read before anything is made.

1. **Contracts** (tasks 1 and 2).
   - `ComposerStartSchema`: `message` (at most 10,000 characters), `repositoryId?`, and `context`. The chips are at most 1 `jira` `{ key }`, at most 3 `pull_request` `{ owner, name, number }` and at most 5 `file` `{ name, text }`, each file's text at most 100 KB in UTF-8. A message that's empty after trimming needs a `jira` chip. `StartSessionRequestSchema` becomes a union of Ship's body and this one, so `POST /api/sessions` serves both and Ship doesn't change.
   - `StartSessionAnswerSchema` gains `context_failed` `{ chip, problem }`. `chip` is the chip's place in `context`, and `problem` is `not_connected`, `not_found`, `unreachable` or `other`. `existing` already covers a ticket with a live session (Q9).
   - The `brief` step becomes `{ key: string | null, message: boolean, pullRequests: string[], files: string[] }`, with defaults, so a saved 011 step (`{ key }`) still parses.
2. **Pure pieces in core** (tasks 3 and 4), each tested as a table.
   - `composer-names.ts`: the title from the message's first line (80 characters, cut on a word, with "…"), and the branch slug (the first five words, ASCII letters, digits and hyphens, at most 40 characters, else `task`).
   - `brief.ts` gains `composerBrief()`, which writes each chip under its own heading: the ticket with its comments and linked issues, each pull request with its branches, failing checks, unresolved comments and the diff (2,000 lines, then counts), and each file under its name. `sessionNote()` learns whether there's a ticket and, without one, says "Do what the user asks in the brief."
3. **Reads** (tasks 5 to 8). Each client is the only file that talks to its network, with MSW fakes in `src/test/fake-jira.ts` and `fake-github.ts`, and each one's no-token-leak test extended.
   - Jira `issueContext()`: `GET /rest/api/3/issue/{key}` with `summary,issuetype,description,comment,issuelinks`, the last 20 comments (author, created, body through `adfToMarkdown`), and the links (the relation's own words, key, summary, status).
   - GitHub `pullContext()`: one GraphQL query for the title, body, base and head refs, the head commit's failed `statusCheckRollup` contexts, and the unresolved review threads (author, path, line, body).
   - GitHub `pullDiff()`: REST `GET /repos/{o}/{r}/pulls/{n}` with `mediaType: { format: 'diff' }`. A 406 ("diff too large") answers `too_large`, and the brief gives GraphQL's file counts instead.
   - `sessions/context-reader.ts`: reads every chip at once with the connections' credentials and gives the brief's chips, or the first chip that failed with its problem. Files pass through as they came.
4. **Starting from the composer** (tasks 9 and 10). The new module `sessions/compose.ts` keeps this out of the 952-line service, and the service wires it in.
   - Answers that make nothing come first, in this order: a live session on the ticket (`existing`), signed out, three working, the folder (Q7 on the server: the id given, else the ticket project's only folder, else `choose_folder`; no folders at all is `no_folder`), then the context read.
   - Then the record: the ticket's summary or the message's title, `source` as the ticket or null, `jiraUrl` and `sprint` for a ticket, and `ticket` from what was read. `run()` takes a start plan (the brief, the branch name, the brief step) from an in-memory map that the composer start fills. A restart never needs it: Orynx halts working sessions when it closes (011). Ship's path doesn't change.
   - Both kinds of start queue behind one key, the ticket's or `composer`, as `start()` does now.
5. **Route and client** (tasks 11 and 12). `POST /api/sessions` parses the union, with a 2 MiB `bodyLimit` on that route, because five 100 KB files can double in size when escaped. The leak test at `LOG_LEVEL=trace` covers a composer start: no message, file text, description, comment or diff line in a log line or an event. `postSession()` takes the union and parses the new answer.
6. **`@devhub/ui`** (tasks 13 to 15).
   - SourceMark gains `orynx`, drawn with `BrandMark` at the same size, for a session with no ticket (Q15b). AttentionRow and the sidebar's SessionItem take it.
   - `ContextPicker`: the + button and one Radix Popover with two views. The kinds view is a `role="menu"` list with arrow keys, rows that lead on, the label and the foot. The list view is a `role="dialog"` with Back, the title and count, a search box that is the ARIA combobox over a listbox (Combobox's pattern), options with a check and `aria-selected`, an extra row ("Add PROJ-9999", "Add local folder…"), the empty line, three Skeleton rows while loading, and the note in the foot. Esc closes it and returns focus to +, and Back returns to the kinds. At 360 px it's at most the window's width less 32 px.
7. **The app** (tasks 16 to 25). Everything lives in `features/home/`.
   - `composer-words.ts` (Q13), `composer-rules.ts` (paste parsing, file checks, Q7's folder choice), and `store.ts` (the draft, the chips in order, the folder and whether you picked it). `persist` keeps only the last used folder id, as `devhub.home`.
   - `components/home-composer.tsx`: react-hook-form with the contract's message rule, the text mirrored into the store as 013 does, the chips, the placeholder, Send, and the answers. `started` navigates and clears the draft. Every other answer shows a line and keeps the draft.
   - `components/folder-picker.tsx`, `components/agent-picker.tsx`, and `components/add-context.tsx` (the kinds, the Jira and Pull request lists from `useSearchIndex()`, Git repository, and File through a hidden `<input type="file" multiple>`).
   - `components/waiting-banner.tsx`: from `useSessions({ recent: true })`, it takes the `needs_you` session with the oldest `updatedAt` and reads its first approval through `useSession(id)`. The events the sidebar already hears keep it live.
   - `components/quick-starts.tsx`: Pick up a ticket links to `/tickets`. Review a pull request sets `?inbox=pull-requests` and moves focus to that tab.
   - The Session screen without a ticket: no Ticket tab, and the brief step names its chips.
8. **e2e, docs and the browser** (tasks 26 to 29). Then the PR of a session with no ticket, once 014 has merged (task 30), then /review.
