## Decision, 22 Oct 2026: reads and writes that ask

The user's ask (22 Oct 2026, item 5 of their list): "even orynx have access to jira and claude also, orynx can't update my jira tickets". Asked how far this spec should go, they picked **reads, plus writes that ask**: Claude searches and reads Jira freely, and comments, changes a status or assigns only after you press Allow on the approval callout that spec 012 already has, with an "Always allow" row in Settings › Coding agent. The token never reaches Claude. This replaces "Claude only reads Jira" below; the Write tools section, AC-13 to AC-19 and Q7 to Q11 are new. Q1 to Q6 still stand.

## Assumptions

Correct these now, or the work goes ahead on them.

- **Three tools, all read-only, on the `orynx` server that already exists.** Claude Code names them `mcp__orynx__<tool>`, as it does the ticket tools.
  - `search_jira`: takes a JQL query and an optional limit (50 by default, at most 100). For each issue it returns the key, summary, type, status and its category, priority, assignee, due date and last update, and it says whether Jira found more. It leaves out descriptions and comments, which `get_jira_issue` reads. It does not page past 100; Claude narrows the query instead. This gets a `shortcut:` comment.
  - `get_jira_issue`: takes one key and returns what the composer's Jira chip reads today (`issueContext()`, specs 015 and 022). That is the summary, type, Markdown description, status, priority, assignee, reporter, due date, labels, the last 20 comments and the linked issues.
  - `list_jira_projects`: takes no input and returns each project's key and name (`projects()`, spec 005). This lets Claude turn "acme" into `MAG`.
- **The token never reaches Claude.** The tools run in Orynx's own process with the saved credentials (`jiraConnection.credentials()`), and only through `integrations/jira/client.ts`. Claude sees Jira's data and never the login: not the site's login, the email or the token. Commands still run in the sandbox with no network.
- **Any JQL is allowed.** Orynx doesn't limit the query. The saved login sees only what you can see in Jira, and Jira's search can't change anything.
- **Each call waits as long as Jira already does**: 10 seconds, the client's `timeoutMs`.
- **The tool's answers to Claude, when something goes wrong** (you see them only through Claude's own words):
  - Jira refused the login: "Jira refused Orynx's saved login. Reconnect Jira in Settings › Connections."
  - Jira can't be reached or is too slow: "Orynx couldn't reach Jira." / "Jira took too long to answer."
  - The issue doesn't exist: "There's no Jira issue MAG-1234, or you can't see it."
  - Jira refused the JQL: Jira's own message (Q6).
  - A failed call adds no step, as with the ticket tools today.
- **Build and Ask sessions both get the tools, and no call asks first.** Reading Orynx tickets works the same way (spec 037, Q5), so both kinds can read Jira.
- **The tools exist only while Jira is connected.** Each run, the first and every follow-up, gets them only if Jira is connected when that run starts. A session that began without Jira gets them on its next follow-up after you connect.
- **Each successful call is a step in Claude's progress**, as Orynx's ticket tools are (spec 037, Q12i). The wording is in Q4.
- **Nothing new outside the tools.** There is no new dependency, endpoint, screen or component. The one contract change is a `jira` activity kind for the steps.
- **Outside agents don't get the tools.** Spec 037's local MCP server for agents outside Orynx stays Orynx tickets only (spec 037, Q14).

## Goal

When Jira is connected in Orynx, Claude can find and read my Jira tickets inside a session the way I would in Jira, without me adding each one as a chip first. Asking "which bugs assigned to me in Acme are on the release branch" just works. When I ask, Claude can also comment on a ticket, move it to another status or assign it, but each change waits for my Allow unless I've said Always allow in Settings › Coding agent. Claude never sees my Jira token.

## Write tools (the decision of 22 Oct 2026)

- **Three more tools on the `orynx` server, each a change in Jira:**
  - `comment_on_jira_issue`: a key and Markdown text, posted as a comment in Jira's own format (ADF, as spec 019 writes it).
  - `transition_jira_issue`: a key and the name of the status to move to. Orynx reads the issue's transitions and picks the one that leads to that status, by the status's id, never by matching a name across a workflow (integration-adapter skill). No such transition: the tool says which statuses it can move to.
  - `assign_jira_issue`: a key and `me`, `nobody` or a person's Jira account id (Q9).
- **Each call asks first, on the approval callout spec 012 draws**, with Allow once, Always allow and Deny. The callout shows what will change: the comment's text, or "MAG-1234: To Do → In Review", or "Assign MAG-1234 to you".
- **Always allow is one row in Settings › Coding agent** ("Claude changes Jira", Q8), off by default. Turning it on lets every Jira change run without asking; the steps still show each one.
- **Each change Claude made is a step**, as reads are (Q10 has the wording).
- **The writes go through `integrations/jira/client.ts` with the saved login**, as the reads do; the token, the email and the Authorization header never reach Claude, a step, a log or `session.json`.

## Out of scope

- Editing an issue's fields (summary, description, labels, priority) or creating issues from a session (Q7). Comments, transitions and assigning are in, since 22 Oct 2026.
- Loading your own MCP servers, plugins or claude.ai connectors (the Atlassian one too) into a session. Q7 of spec 011 stands.
- Jira tools for agents outside Orynx, through spec 037's MCP server.
- Tools for Claude to read GitHub or Slack.
- Paging past 100 issues in one search. Attachments, worklogs, an issue's history, and boards or sprints through Jira's agile API are out too; JQL's `sprint in openSprints()` covers the current sprint.
- A switch to turn the tools off (Q2).
- Checking a branch in an Ask with no folder. That belongs to the session kind (spec 031).
- Caching Jira's answers: each call asks Jira.
