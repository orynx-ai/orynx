# Connect GitHub

Status: approved
Roadmap: Phase 1 — Foundation

## Assumptions

Correct these now, or the work goes ahead on them.

- **github.com only.** DevHub sends a GitHub token to `https://api.github.com` and nowhere else. GitHub Enterprise Server and other gh hosts are out of scope, the way Jira Server was in 003.
- **Two ways to connect, and you pick one in the form.** "Use my gh login" or "Use a personal access token". DevHub saves only which one you picked, in `<DEVHUB_HOME>/settings.json` as `"github": { "method": "gh" }` or `{ "method": "token" }`. Your GitHub login name is not saved; the status check learns it each time.
- **The gh way never copies your token.** Each time DevHub needs a token, it runs `gh auth token --hostname github.com` and keeps the answer in memory for that one call (Q2). It never runs `gh auth login`, `gh auth logout` or any other gh command that changes something, and Disconnect leaves gh signed in. gh gets at most 5 seconds to answer.
- **Finding gh doesn't run it.** The form looks for an executable named `gh` on the server's PATH, without starting it, so it can pick the gh choice for you when gh is there. gh runs only when you press Connect GitHub with the gh choice, or when the status check needs a token for a saved gh connection.
- **The token way works like Jira.** The token goes to the keychain (account `github`), and the `.env` fallback from spec 002 (`DEVHUB_GITHUB_TOKEN`) still works. Switching from a token to gh deletes the saved token from the keychain, so DevHub keeps one way at a time.
- **Connect checks first, then saves.** DevHub asks GitHub who the token belongs to (`GET /user`). It saves only when GitHub says yes, and the token can read private repositories (Q3). On any failure nothing changes, and an existing connection stays as it was.
- **"Connected" means GitHub accepted the token**, checked the same way as Jira: at most once every 2 minutes, one check shared by everyone asking, at most 10 seconds for GitHub, and nothing polling in the background. With the gh way, each check asks gh again, so signing out of gh or switching gh accounts shows up within 2 minutes or on the next restart.
- **The library is `@octokit/rest`.** `docs/architecture.md` lists it as planned for this spec. It goes into `@devhub/core` only, through `pnpm add`, and loads on the first call (I'll measure its import time, as 003 did for jira.js). Its only caller is `packages/core/src/integrations/github/client.ts`. Running gh lives in `integrations/github/gh.ts`, the only file that starts gh.
- **New endpoints:** `GET`, `PUT` and `DELETE /api/github/connection`. GET returns the saved method, whether `.env` holds a GitHub token, and whether gh was found. It never runs gh or reads the keychain. No new error codes: GitHub refusing the token, a missing scope and every gh problem are `integration_rejected` (422), and the network, a timeout, the rate limit or a GitHub error are `integration_unreachable` (502), with the problem's message. The form shows a rejected answer under the token field, or under the choices for the gh way, and an unreachable one on a single line above the buttons.
- **The token stays inside `client.ts` and `gh.ts`.** gh's output is read only by `gh.ts` and is never logged. A failure from gh keeps only its exit code. An octokit error becomes a problem of ours with a fixed message. The logger already redacts every `authorization` header (003).
- **Tests and e2e never use your real gh.** Core tests start a small fake `gh` program instead, and fake GitHub with MSW. The e2e run puts a fake `gh` first on the server's PATH and keeps `DEVHUB_KEYCHAIN=memory`, so it can't read your gh login or your keychain.
- **After Connect succeeds**, the form closes, focus returns to the row's Manage button, and a polite status message says "GitHub is connected.", as with Jira.

## Goal

I connect GitHub once from Settings, either with the gh login I already have or with a personal access token. DevHub checks with GitHub before keeping anything, never keeps a copy of my gh token, and the GitHub row says in words which account it uses and whether the connection works. When it doesn't, the row says why and what to do.

## Out of scope

- Reading review requests, your PRs, checks and review comments (Q1 moves them to spec 007), and the SQLite cache.
- Pushing the session branch and opening the PR (spec 014).
- GitHub Enterprise Server, other gh hosts, OAuth apps, GitHub Apps, and more than one GitHub account.
- Finding out whether a token is authorized for your company's single sign-on. GitHub only says so when a repo is read, so spec 007 reports it.
- Signing in or out of gh from DevHub.
- Showing your GitHub name in the sidebar footer.
- Jira's longer messages wrapping at 360 px (left from the 003 review) and the other Settings tabs (spec 005).
- Checking GitHub in the background on a timer (spec 007).
