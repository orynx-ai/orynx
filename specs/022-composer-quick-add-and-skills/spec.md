Roadmap: not on the roadmap. The user's feedback on Home and Tickets, 19 Oct 2026. It takes 022, the next free number: 021 is kept for `021-after-the-merge`.

## Assumptions

Correct these now, or the work goes ahead on them.

- **One spec for seven asks.** The user asked for seven changes in one message, so they share one spec and one branch, `feat/022-composer-quick-add-and-skills` in `../dev-hub-022`, from `origin/main` at PR #24 (015 merged). The user's own checkout (`docs/spec-neutral-company`, with an uncommitted `docs/product/spec.md` edit) isn't touched. The parts: A several chips, B files by path, C the chip strip and its dialog, D one action on Home's rows, E Ship adds to the composer, F the ticket dialog, G skills. Acceptance criteria are grouped by part, and the work is built in that order, so G can move to a spec of its own if it runs long (Q1).
- **It changes what 015, 020 and 008 decided.** 015 Q2 (one ticket), Q5 (text files up to 100 KB, read in the browser) and its limits; 020's Ship and the row icons on Home; 008 Q4a (a card's title opens Jira or the session). `docs/product/spec.md` says a card's title opens "the ticket detail in a side panel"; the user asked for a dialog (Q8).
- **"Build" is Ship.** Spec 020 renamed Build with Claude to Ship everywhere. Ask 5 means the sparkle on a Tickets card and the Ship button in the Tickets list.
- **A. Several tickets.** The first ticket you add is the session's ticket: it names the branch (`feat/PROJ-1423`), the session's title and source, the Ticket tab, the pull request's Jira line, the folder (015 Q7) and the "already has a session" check (015 Q9). Every other ticket is context only, and Claude gets the same for each: summary, type, description, the last 20 comments and linked issues (015 Q3). Removing the first chip makes the next ticket the session's ticket (Q2).
- **B. Files by path.** A file chip holds the file's full path, not its text. Nothing is read in the browser or by Orynx. A browser never tells a page a file's path, so File from this computer asks the local server to open the computer's own file picker, as Choose folder does (spec 020, AC-35), with several files allowed. Claude gets each path in the brief and may read exactly those files, wherever they are, and never edit them. Everything else outside the worktree stays refused (011 Q6). Claude Code's own Read tool reads text, images, PDFs and notebooks, so Orynx checks no type and no size (Q4).
- **A file is checked at Send.** The server checks each path is still a file it can read. If not, nothing starts and the line names the file. A file whose name looks like a secret (`.env`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, spec 014 Q6's list) is never added (Q4).
- **C. Two chips, then +N.** The composer shows the first two chips in the order you added them, then a chip-shaped button "+3". It opens a dialog with the tabs Tickets, Pull requests and Files, each listing what you added with a Remove button (Q6, Q7).
- **D. One action on a Home row.** A Jira or pull request row loses Ship and the Open in Jira or GitHub arrow, and gets one + button whose tooltip reads "Add to composer". It adds the chip to the composer on the same page; it doesn't scroll or move focus. Pressed again, it takes the chip out (Q3). A row for a waiting session keeps its Open session arrow, since it stays inside Orynx.
- **Row titles.** A Jira row's title opens the ticket dialog (F). A pull request row's title still opens GitHub in a new tab, now without the arrow. That one place gives way on the user's 18 Oct 2026 call that every link leaving Orynx shows the arrow (Q3).
- **E. Ship adds to the composer.** Ship no longer starts a session. It adds the ticket's chip after any chips already there, opens Home and puts focus in the box. Ship's folder menu (Start in, Add local folder) goes, because the composer's folder picker does that job (015 Q7) (Q13).
- **F. The ticket dialog.** A Jira ticket's title opens a dialog with the ticket in full, read from Jira when it opens, and Open in Jira at its end. It opens from Home's rows, Tickets' cards and list, and ⌘K's results. The session's Ticket tab stays as it is (Q8).
- **G. Skills.** Typing `/` at the start of the box, or after a space or a new line, opens a list of skills, as Claude Code's terminal does. They come from the folder the picker shows (its `.claude/skills/*/SKILL.md` and `.claude/commands/**/*.md`) and from yours (`~/.claude/skills`, `~/.claude/commands`) (Q10). Picking one puts `/name ` in the box. At Send, each `/name` that is a listed skill adds that skill's file to the brief under its own heading, and Claude may read (never edit) inside that skill's folder (Q9).
- **Claude's settings don't change.** `settingSources: []`, hooks off and `strictMcpConfig` stay (011 Q7). No hook, MCP server, plugin or allow rule from the repository or `~/.claude` comes along with a skill, and a skill's `allowed-tools` line is ignored (Q9).
- **The skills are read when you type `/`**, once per folder while the page is open, by a new server read. It reads only file names and each file's frontmatter (`name`, `description`); the skill's text is read at Send.
- **Limits** (Q5). At most 10 tickets, 10 pull requests, 20 files and 5 skills a session. No limit on a file's size or type. The message stays at most 10,000 characters (015). A pull request's diff still goes up to its first 2,000 lines, then counts only.
- **The brief is still exactly what you see** (agent-runtime rule 5): your message, then each chip in the order you added it, then each skill you named. Files go as paths. `brief.md` holds it (0600). Logs and events carry ids, keys, counts and file names, never a file's contents, a skill's text, a description or a comment.
- **New reads, no new writes.** Jira: one issue in full for the dialog (`GET /rest/api/3/issue/{key}` with the fields Q8 lists, `comment` and `issuelinks`), through the Jira client. The computer: a file picker, run as 020's folder picker runs (`osascript` on macOS, `zenity` or `kdialog` on Linux), and the skill files. Nothing is written to Jira, GitHub, the repository or `~/.claude`.
- **The draft still lives in the page** (015 Q14): chips added from a row or from Tickets go into the same zustand store, so they're there when you come back to Home, and a reload clears them.
- **Tests.** Core tests fake Jira with MSW, the file picker with a fake program on a test `PATH` (as 020's folder picker), and skills with temporary folders standing in for the repository and `~/.claude`. Nothing reads the real `~/.claude`, `~/.devhub` or a real repository.
- **`docs/product/spec.md` isn't edited here.** The branch leaves the user a script for its changes (Home's row actions, Ship, the card title, the + menu's File row, skills), as 015 did.

## Goal

From Home's list or the Tickets board I drop the tickets and pull requests I want into the composer with one click each, add any file from my computer by its path and a skill from the repository with `/`, then say what I want and press Send. Clicking a ticket shows me the whole ticket inside Orynx first, with Jira one click away.

## Out of scope

- A dialog for a pull request. Its title still opens GitHub.
- Changing a ticket from the dialog (status, assignee, comments). The dialog only reads.
- A + on Tickets' cards that stays on Tickets, unless Q13 says otherwise.
- Folders as context. A file chip is one file.
- Dragging files onto the composer. A browser never gets a dropped file's path.
- Claude Code's own commands (`/clear`, `/compact` and the rest), plugins' skills and MCP prompts in the skills list.
- Letting Claude Code load skills itself, and a skill's hooks, MCP servers or `allowed-tools` (Q9).
- Skills and context in a follow-up. Follow-ups stay text only (013).
- Slack threads as context (016).
- Keeping the draft across a reload (015 Q14).
- Editing `docs/product/spec.md`.
