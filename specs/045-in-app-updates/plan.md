# Plan: In-app updates, version and what's new

Spec: `specs/045-in-app-updates/spec.md`

## Spec changes found while planning (confirm with "go")

- **Open pages after an update (F).** Every hub start makes a new session token (`apps/server/src/runtime-file.ts`), so a page left open gets a 401 after any restart and already shows the "Orynx restarted · Reload the page to reconnect." notice (`packages/app/src/shell/app-shell.tsx`, `StaleNotice`). The page can't keep working until it reloads, and it can't ask the new hub for its build without the new token. So AC-31 becomes "the existing Orynx restarted notice shows, and Reload opens the new version", AC-33 goes, `/api/status` gains no `build`, and Q6's words aren't used. The page that pressed Update reloads itself (AC-25).
- **AC-5's story.** `packages/app` has no Storybook, so the About panel's axe check is `expectNoAxeViolations` in its own test, as the other Settings panels do.
- **Linux re-runs of `./install.sh` always ask for sudo** (it copies the certificate and runs `update-ca-certificates` every time). Updating from inside Orynx can't answer a password prompt, so `./install.sh` skips the copy when the trusted file is already the same, and fails at once with a clear line, instead of waiting for a password, when there is no terminal.

## Order of work

1. **Contracts** (`packages/contracts/src/updates.ts`): a release, the updates answer (current version and kind, last check, problem, releases, and the update's state), the install request and its refusals, the `updates.changed` event, the `update_available` notification and `testing` builders. Everything else parses these.
2. **Pure core** (`packages/core/src/updates/versions.ts`): parse `v0.1.37`, compare, and read `git describe` output. Fully tested with plain data.
3. **The releases client** (`packages/core/src/integrations/releases/client.ts` and `map.ts`): one `GET` with no token, GitHub's problems as the GitHub client names them (`rate_limited`, `unreachable`, `timeout`, `github_error`), drafts and prereleases left out. MSW fakes `api.github.com`.
4. **The update service and routes** (`packages/core/src/updates/update-service.ts`, `routes/updates.ts`): check at start, every 6 hours and on demand at most once a minute, keep the answer in memory, log a failed check, refuse Update while a session works or waits, and tell once per version (the version is remembered in `settings.json`, so Clear cache doesn't tell again). The service takes an `UpdateHost` from the host: its kind, its version, and what Update and Restart do. `createServer()` without `updates` never checks, so no test or e2e hub reaches GitHub by accident.
5. **The clone updater** (`packages/core/src/updates/clone-updater.ts`): `git describe` for the version, refusals for a clone with changes of its own or one that can't fast-forward, then `git pull --ff-only && ./install.sh` in a detached runner writing `<DEVHUB_HOME>/update.log`. Tested with real temporary repositories, a bare origin and a fake `install.sh`.
6. **`install.sh` and the server host**: `DEVHUB_SERVICE` in the LaunchAgent and the systemd unit; the Linux sudo skip; `apps/server` config (`DEVHUB_SERVICE`, `DEVHUB_RELEASES_URL`) picking the kind (desktop when `process.parentPort` exists, service, or by hand) and handing the clone updater or the desktop bridge to `createServer()`.
7. **The desktop app**: the hub ↔ Electron messages over the `utilityProcess` port (state in, download and restart out, each side parsing with zod), `updates.ts` without the native dialogs (Q5), Linux's Restart to update through `quitAndInstall`, then the Mac's own download, sha512 check, unzip and swap (`mac-update.ts`), falling back to Download when the folder can't be written.
8. **api-client**, then the **About tab** in Settings: Version, Updates (every state, AC-6 to AC-30), What's new (AC-14 to AC-17), and the notification's words and place (AC-13).
9. **Release notes** from `feat` and `fix` commits (`scripts/lib/release-notes.ts`, `release.yml`), then the e2e runs, then the docs.
