# Orynx tickets: Orynx's own tickets beside Jira's

Status: approved
Roadmap: not on the roadmap. This is the user's ask from 20 Oct 2026: "an Orynx in-house ticket system … claude or the user can use it for creating, updating, deleting tickets … a source filter which lists Jira and Orynx, along with create buttons, and full CRUD on that ticket, a similar approach to Jira". The spec takes 037, the next free number after 036 (the session terminal draft). The branch is `feat/037-orynx-tickets` in `../dev-hub-037`, made from `origin/main` at PR #41. It overlaps the roadmap's unbuilt `019-new-ticket`, which puts the column + and a New ticket form in front of Jira (see Q1). Approved 20 Oct 2026: the user took every recommendation and widened two of them. Any agent, inside Orynx or outside it, can use the tickets (Q14). Every control comes from shadcn, following the design (Q15).

## Assumptions

Correct these now, or the work goes ahead on them.

- **An Orynx ticket lives on this laptop only.** It is stored in a new file, `~/.devhub/tickets.json`, in `DEVHUB_HOME` beside `settings.json`. It is written the same way: to a temporary file that is then renamed, with mode 0600. It is not kept in `cache.db`, because Clear cache wipes that file and remakes it whenever it can't read it. Each change rewrites the whole file, which is fine at the few hundred tickets one person keeps. This is a `shortcut:` comment that tells a later spec to move to SQLite past a few thousand tickets. No new dependency is needed.
- **A file Orynx can't read is never saved over.** The file is renamed to `tickets-<date-time>.unreadable.json`, as `settings.json` is today (spec 027). Orynx starts an empty list, and the Tickets screen names the kept file once (Q12j).
- **Keys follow Jira's shape: `ORX-1`, `ORX-2`, and so on (Q4).** A deleted ticket's number is never used again. The key passes the existing ticket-key schema, so branches (`feat/ORX-12`), chips and the brief take it as they take a Jira key. The `ORX` prefix belongs to Orynx: a Jira project called ORX would clash, so the key alone decides which source a ticket comes from.
- **The fields are Jira's core ones, and no more (Q3).**
  - Title: required, 255 characters at most.
  - Description: Markdown, 32,000 characters at most, drawn by `@devhub/ui`'s `Markdown`, which draws no raw HTML.
  - Type: Task, Bug or Story. The default is Task. A Bug counts as a bug for the Type filter and is red on the card, as in Jira.
  - Priority: Highest, High, Medium, Low or Lowest, with Medium as the default. These map onto the card's existing priority bars.
  - Status: To do, In progress, In review or Done, the board's four columns. The default is To do, or the column whose + you pressed.
  - Due date: optional.
  - Orynx records who made the ticket (you, or Claude in a named session), when it was made, and when it last changed. You never edit these.
- **Every Orynx ticket is yours.** Orynx has one user, so it has no assignee field. The Assignee filter's "me" includes Orynx tickets, and the card shows your avatar.
- **Orynx tickets have no sprint.** They show whichever Jira project or sprint is picked, because the pickers choose Jira's tickets only. When only Orynx is ticked, the pickers hide and the breadcrumb reads "Tickets / Orynx" (Q7).
- **Done keeps a Jira Kanban board's two weeks.** An Orynx ticket shows in Done for 14 days after it moved there. After that it leaves the board and the list, but ⌘K still finds it (Q6).
- **The Source filter is a sixth `FilterMenu`, placed before Assignee.** It is ticked Jira and Orynx by default and lives in the URL, as spec 020's filters do. With Orynx unticked, New ticket and the column + hide, so a new ticket can never land somewhere you can't see it.
- **Tickets works without Jira.** Today the whole page is "Connect Jira" when Jira isn't connected. With this spec, the page shows Orynx tickets with one line linking to Settings › Connections. The Source filter and the pickers hide, because they have nothing to choose (Q7).
- **Create.** You can create a ticket in two places:
  - a "New ticket" button in the page bar (secondary, so Tickets still has no filled button);
  - the + in each column head, which `tickets.html` already draws and `BoardColumn`'s `action` slot already holds.

  Both open one dialog built from `Dialog`, `Field`, `Input`, `Textarea` and `Select`, with react-hook-form and the contract's zod schema. Due is a `DatePicker` (Q15).

- **Read.** An Orynx ticket's title opens the existing ticket dialog (spec 022). The dialog shows the Orynx mark (`SourceMark` already has `orynx`) and no "Open in Jira" button.
- **Update.**
  - Status in the dialog is a picker that saves as soon as you change it, as Jira's does. This is how a ticket moves between columns, since there is still no dragging.
  - Edit turns the dialog into the same form as New ticket.
  - Saving sends the version you opened. If Claude or another tab changed the ticket since, the form says so and keeps your edits. A second Save writes over the newer version.
- **Delete.** A "Delete ticket" button in the dialog opens an `AlertDialog`, with Cancel focused first and the buttons at the end (Cancel, then Delete ticket). There is no undo. A session started from the deleted ticket keeps its brief, and its Ticket tab says the ticket was deleted (Q8).
- **Any agent can use Orynx tickets (Q14).** There is one set of ticket tools, defined once in `packages/core` and naming no agent. Each tool has a name, a description, a zod input from `@devhub/contracts`, and a handler that calls the same ticket service the routes call. The tools are list (with the board's filters), get, create, update and delete. They never reach Jira tickets and never touch a file. Two doors open onto that one list:
  - **Inside Orynx: a session's agent gets the tools in-process.**
    - For Claude, the tools come through an SDK MCP server named `orynx`. The SDK we ship (0.3.302) already has `createSdkMcpServer`, so this needs no new dependency. Today `mcpServers` is `{}` with `strictMcpConfig: true`, and this adds that one server only.
    - `AgentAdapter` takes the tool list, so a later agent mounts the same tools through its own adapter.
    - In a Build session, reads, creates and edits run without asking. Each one shows as a step in the agent's progress ("Created ORX-14 · …"), and the key opens the ticket dialog.
    - Delete always asks, through spec 012's approval callout, with Allow once and Deny and no Always allow.
    - An Ask session gets the read tools only, because Ask "changes nothing" (spec 031).
  - **Outside Orynx: a local MCP server lets any MCP client use the same tools.** That includes Claude Code in a terminal, Cursor, Codex and VS Code.
    - The server uses `@modelcontextprotocol/sdk`, which `docs/architecture.md` already lists as the Agent SDK's peer.
    - It is off until you turn it on in Settings › Coding agent. There, "Copy MCP config" gives you the config to paste into the other tool.
    - It answers on 127.0.0.1 only and checks the Host header, as every route does. It also checks its own agent token, which is kept in the keychain and is never the page's session token. Turning the row off and on makes a new token.
    - The copied config keeps working when Orynx restarts, and in the desktop app, whose port changes at each launch. /plan picks how: a small stdio command that finds the hub through `runtime.json`, or a fixed address.
    - Outside agents read, create and edit tickets. Delete is refused with a line telling the agent to ask you, because there is no session to show an approval in.
    - A ticket an outside agent makes says who made it, by the name its MCP client gives ("Created by Cursor").
- **Built from shadcn, following the design (the user's ask, 20 Oct 2026).**
  - Every control is a `@devhub/ui` component taken from shadcn and restyled to the tokens. The layout follows `tickets.html`, `docs/design/design-system.md` and the clean-ui skill. No component is styled inside a feature.
  - `@devhub/ui` already has Dialog, Field, Input, Textarea, Select, Button, Tooltip, FilterMenu, Switch and CopyButton.
  - These come new from shadcn, each with a story for each state and a test:
    - `AlertDialog`, for Delete ticket's confirmation. It is Radix AlertDialog, already in `radix-ui`.
    - `Popover` with `Calendar`, as a `DatePicker` for Due (Q15). Calendar needs `react-day-picker`, the spec's one new dependency, which gets its row in `docs/architecture.md`.
- **What a person and Claude can do is the same as what the API allows.** The routes check every body against the contract (Rule 2), so neither the browser nor Claude can store a ticket the form would refuse.
- **Live everywhere.** Any change, from you, Claude or another tab, publishes a server event. Every open Tickets page, ticket dialog, sidebar count and ⌘K list then refreshes from it.
- **Starting work on an Orynx ticket works as it does for a Jira ticket.**
  - Ship adds its chip to Home's composer, with the Orynx mark. Pasting `ORX-12` makes the same chip, and Add context's ticket list holds Orynx tickets too.
  - Send makes `feat/ORX-12`, and the brief says "Orynx ticket ORX-12" with its fields.
  - The folder is the composer's folder picker. That is what happens today for a Jira ticket whose project has no folder in Settings › Repositories, so an Orynx ticket needs no folder field.
  - One live session per ticket, as today.
- **The sidebar's Tickets count adds your Orynx tickets that aren't Done.**
- **Orynx changes no ticket status by itself** (Q9). Moving ORX-12 to In review when its PR opens is a click, or something Claude does with its tool.
- **This conflicts with unmerged work.** Batch 028 (`../dev-hub-028`, not merged) also changes the Tickets screen, adding checkboxes and a floating bar. Whichever merges second takes the conflicts. Bulk actions on Orynx tickets wait for both.
- **People-owned files.**
  - `docs/product/spec.md` says Tickets "shows your current Jira sprint". It also says the column + "creates the issue in Jira", and its data table has no `tickets.json`.
  - These lines need the user's edit (Q1, Q13). This spec doesn't change them, and the agent can't commit them.

## Goal

Besides Jira, I can keep tickets in Orynx itself. I create, open, edit, move and delete them on the Tickets screen the way I would in Jira, and Claude, or any other agent inside Orynx or outside it, can file and update them while it works. A Source filter shows Jira's tickets, Orynx's, or both, and an Orynx ticket starts a session the way a Jira ticket does.

## Out of scope

- Creating, editing or deleting Jira tickets. Spec 019 keeps Jira's New ticket (Q1).
- Dragging cards between columns. Version 1 still has no dragging. Status moves through the dialog.
- People: assignees, sharing Orynx tickets with teammates, or syncing them between laptops. Also export, import, and moving a ticket from Orynx to Jira or back.
- Comments, attachments, labels, links, subtasks, epics, sprints, estimates and a history of changes (Q3).
- Your own statuses, types or workflows.
- Bulk actions on Orynx tickets. Batch 028's floating bar picks this up after both merge.
- Orynx tickets in Home's attention list or in notifications.
- Undo, or a trash, for deleted tickets.
- Outside agents deleting tickets, starting sessions, or reaching anything but Orynx tickets: Jira, sessions, pull requests or files (Q14).
- A token or permissions for each outside agent. Every outside agent shares one token.
- Reaching the MCP server from another computer.
- Orynx moving a ticket's status by itself when a session starts or a PR opens (Q9).
- A folder field on a ticket. The composer's folder picker decides.

## Design

none. `docs/design/screens/tickets.html` draws only the column +, an icon button with nothing behind it. It shows no Source filter, New ticket form, edit view, delete confirmation, date picker or Other agents row. The user asked for everything to come from shadcn and follow the design (20 Oct 2026), so the spec uses:

- `tickets.html`'s board, list and column +, with spec 020's `FilterMenu` for Source;
- spec 022's ticket dialog, and `SourceMark`'s `orynx`;
- for the form: `@devhub/ui`'s shadcn `Dialog`, `Field`, `Input`, `Textarea` and `Select`;
- new from shadcn: `AlertDialog`, `Popover`, `Calendar` and `DatePicker`;
- for Settings › Coding agent: `SettingRow`, `Switch` and `CopyButton`.

Q10, Q11 and Q15 hold the decisions a design would make.
