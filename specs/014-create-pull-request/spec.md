Roadmap: Phase 3 — Claude sessions

## Assumptions

Correct these now, or the work goes ahead on them.

- **What 014 builds on.** 011 and 012 are merged (PR #19, PR #20). 013 is being built in another session: on 18 Oct 2026 its spec was approved and planned, with no task built yet. 014 needs 013's code in one place only: what the follow-up box does once a PR is open (AC-19). Everything else uses what 011, 012 and 004 already built: the session with its worktree and branch, the title row, the stepper, Claude's progress, Discard, and the GitHub connection. This branch starts from `main` at PR #20. Q1 asks whether to build beside 013 or after it.
- **What 014 takes over.** From 011: Create pull request in the title row, pushing, and the PR open state. From 013: follow-ups once a PR is open. Removing worktrees after a PR merges, which 011 also sent here, is Q8.
- **Nothing reaches GitHub without your click** (agent-runtime rule 4, CLAUDE.md rule 11). Orynx commits, pushes and opens the PR only when you press Create pull request in the dialog (Q3), and pushes again only when you press Push changes (Q7). Claude finishing, a follow-up, a restart and opening the dialog push nothing. Claude's own `git push` and `gh pr create` stay refused (012 Q7).
- **Where the push goes.** To the folder's `origin`, and only when `origin` is on github.com (004: only github.com). Orynx pushes only the session's own branch (`feat/PROJ-1423`), named on both sides of the push, so nothing else on `origin` can change. It never forces. The default branch never gets a push. Your main checkout's branch, files and index don't change; only its `.git` learns that the branch was pushed.
- **How the PR opens.** `POST /repos/{owner}/{repo}/pulls` through 004's `client.ts`, the only file that talks to GitHub, with the connection's token: gh's for the gh way, the saved one for the token way. The base is the branch the session started from (011's `base`: `origin/main` gives `main`). When that branch wasn't on `origin`, the base is the repository's default branch on GitHub. A PR's link must be https on github.com, or it isn't kept (as in 007).
- **What the dialog says will happen is worked out from the worktree.** "Changed files" means what isn't committed yet: changed files, and new files git doesn't ignore. The diff Claude drafts from runs from where the branch started (`git merge-base` with the branch it was made from) to the worktree on disk, so it matches 013's Changes tab (013 Q4).
- **The API.** Each body is a schema in `@devhub/contracts`.
  - `POST /api/sessions/:id/pull-request/draft`: Claude's title and description (Q4), what will happen (how many files Orynx commits, the branch, the repository, the base), or why there can't be a PR (Q11c). It's a POST because each call asks Claude.
  - `POST /api/sessions/:id/pull-request` with `{ title, body }`: commit, push, open. It answers with the PR's number and link, or what went wrong (Q11d).
  - `POST /api/sessions/:id/push/draft` and `POST /api/sessions/:id/push` with `{ message }`: Push changes (Q7).
  - `GET /api/sessions/:id` carries `pullRequest` (number, link, repository) once there is one.
- **What the session keeps.** `session.json` gains the PR's number, link and repository, when it opened, and the commit Orynx last pushed. A session saved before 014 has no PR and still reads. The terminal log names the session, the ticket, the PR number and a problem's code. It never holds the title, the description, the remote's address, a path or git's output, because git's output can hold the remote's address with a password in it.
- **One at a time.** A session does one create or push at a time, so two tabs pressing Create get one commit, one push and one PR. Discard waits until a push has finished.
- **Time limits.** Claude's draft: 60 seconds. The push: 2 minutes. Each GitHub call: 10 seconds (004).
- **No new dependency.** simple-git, @octokit/rest and the Agent SDK are already listed in `docs/architecture.md`. The description field needs a component `@devhub/ui` doesn't have (Q10b).
- **Tests never reach GitHub, push to a real repository or run the real Claude Code.** Core tests fake api.github.com with MSW (`test/fake-github.ts`). They push to a temporary bare repository that stands in for `origin` on github.com, in a temporary `DEVHUB_HOME`, and fake the draft at the SDK's boundary. The e2e fake Claude Code learns to answer a drafting call, and the e2e hub's fake GitHub learns to open a PR.

## Goal

When Claude is done and the change looks right, I press Create pull request. Claude has already written the title and description. I fix them if I want, press Create, and Orynx commits, pushes the branch and opens the pull request on GitHub, linked to the Jira ticket. Nothing leaves my laptop until I press it. If a reviewer asks for changes, I ask Claude, then push them to the same pull request with one more press.

## Out of scope

- Watching the PR once it's open: its checks, reviews and comments, whether it merged or closed, and removing the worktree after a merge (Q8). Home's Pull requests tab picks the PR up at its next sync, as it does any PR of yours (007).
- Reviewers, assignees, labels and milestones, editing the PR from Orynx after it opens, and turning a draft PR into a ready one.
- Forks, pushing anywhere but `origin`, GitHub Enterprise Server, and remotes on GitLab or Bitbucket.
- Bringing the branch up to date with the default branch, rebasing, merge conflicts, and squashing Claude's commits.
- Moving the Jira ticket. Your Jira automation can do that when the PR opens (product spec, "Tickets").
- Sessions without a ticket (015), and sessions on an existing PR's branch ("Fix", 020).
- The More actions (⋯) menu in the page bar: still nothing goes in it (011).
- Changing your git settings, and signing commits in place of git.
