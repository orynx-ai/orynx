## Assumptions

Correct these now, or the work goes ahead on them.

### 1. Orynx reads your ask before it starts (Q1)

- **One quick call at Send, for a Build session only, on the model and effort the composer picked** (Q1). Before the worktree, Orynx asks that model one question with no tools, through `AgentAdapter.write()` with new `model` and `effort` options. It gives up after 30 seconds. Ask sessions skip it: they need no branch and no steps.
- **The page opens at once.** The session exists from Send, as today; the quick read is its first row, so the wait is never a blank screen or a spinning Send button.
- **What the call gets** (about 2 KB, never file contents): your message; each chip's one line (ticket key, type and summary; PR number, title, branch and whether it's yours; file names); the folder's name, its default branch and its `origin` branch names (up to 200, names only, so "latest develop" can be matched); the repository's branch rules (section 2); and the names of your own last 20 branches in that repository.
- **What it answers**, parsed with a zod schema (its steps with `@devhub/contracts`' `SessionStepsSchema`), so a bad answer is a failed one:

  | Field    | What it is                                                                                                        |
  | -------- | ----------------------------------------------------------------------------------------------------------------- |
  | `intent` | `change` (edit code), `run` (start, pull, install, migrate, seed, run tests), `answer` (explain, find, review)    |
  | `title`  | The session's title, at most 80 characters: "Pull develop and start the dev server", not the message's first line |
  | `branch` | A branch name and where its shape came from (`message`, `repo_rules`, `your_branches`, `orynx`), or none          |
  | `base`   | The branch to start from when you named one ("latest develop" → `develop`), else none: the default branch         |
  | `steps`  | The steps this session should show, by the rules of section 3                                                     |

- **Orynx checks every field, and never trusts the model further than that.** A base that isn't on `origin` falls back to the default branch, with a note. A branch name that fails `git check-ref-format --branch`, is over 60 characters, or drops the ticket's key is replaced by today's name. A taken name gets `-2`, `-3`, as today. Steps that break section 3's rules are replaced by the intent's default steps.
- **When the call fails** (Claude not logged in, offline, slow, a bad answer), the session starts exactly as it does today, and the first row says so: "Couldn't read your ask, so the usual steps are shown". A failed read never blocks a session.
- **It's a row you can see.** The first row of Claude's progress is "Reading your ask…" while the call runs, then, done: "Run the app · from develop · no branch yet". Its details list the branch and where its shape came from ("from the repository's git-workflow skill"). This row replaces nothing; the worktree and brief rows follow it as today.
- **Your switch still wins.** The quick read never turns Ask into Build or Build into Ask. Inside a Build session it only picks the intent, the title, the branch name, the base and the first steps. This reverses spec 031's out-of-scope line "Letting Claude choose the kind", for the Build kind only.

### 2. Branch names that fit the repository (Q2, Q3, Q4, Q6)

- **Every Build session works in its own worktree** (Q2), as today, so your own checkout is never touched (CLAUDE.md rule 11) and two sessions can run side by side.
- **The branch is made at Claude's first edit, not at Send** (Q6). Every Build session's worktree starts on a detached HEAD at the fetched base, as spec 031's "your PR" session already does. Orynx makes the branch (`git switch -c <name>`) the moment Claude's first edit is allowed, or when you press Create pull request with no branch yet, whichever comes first. So a run, an answer or a session Claude ends without edits never leaves a branch behind, and a run that turns into a fix gets its branch exactly when it needs one. Until then the header says "No branch yet".
- **Where the name's shape comes from, first match wins** (Q3):
  1. **Your message or a chip.** "on branch mai-2161-fix-login", "use fix/login-redirect": used as written.
  2. **The repository's written rules.** Orynx reads, read-only and capped at 8 KB in all: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `.github/CONTRIBUTING.md`, and every `.claude/skills/*/SKILL.md` whose text says "branch". It passes only the paragraphs that mention branch names. acme-app gives `feature/<short-description>` and `fix/<short-description>`.
  3. **Your own recent branches there**: the 20 newest local and `origin` branches whose last commit has your git email, names only. acme-app would give `rakesh.dhariwal/<key>-<words>`, but its written rules come first.
  4. **Orynx's own**: `feat/<KEY>` with a ticket, as today; otherwise `<type>/<three-to-five-words>`, `type` being `feat`, `fix` or `chore` as the quick read judges the work.
- **A branch you named that already exists** (Q4): if it's on `origin`, the worktree starts from it and the first edit makes a branch of that same name, so Create pull request adds onto it, never with force, or links its open pull request, as spec 014 does. If it's only local, the session takes the next free name (`-2`) and the reading row says so.
- **A ticket's key is always in the name** when the session has a ticket. acme-app's `prepare-commit-msg` hook reads the key from the branch name for its `Refs:` footer.
- **The name says what the work is, not how you asked**: `fix/login-redirect-loop`, never `feat/take-a-pull-from-latest`.

### 3. Steps Claude names, at most five, that change while it works (Q5)

- **Claude names the steps** (Q5), first in the quick read's answer, then while it works. Each step has:
  - a **label**, Claude's words, shown in the stepper;
  - a **kind**, never shown, from `setup` · `plan` · `build` · `test` · `run` · `answer` · `review` · `pull_request` (shown as Push on your own pull request, as spec 031 does). The kind tells Orynx when the step moves on and who moves it.
- **The rules are strict. A list that breaks any of them is refused whole, never trimmed or fixed:**
  - 1 to 5 steps in all, Pull request and Push included.
  - A label is 1 to 3 words and at most 16 characters, starts with a capital letter, and holds only letters, digits and spaces. No two labels in a list are the same, and no two kinds.
  - Pull request (Push on your own pull request) is only ever the last step, and its label is Orynx's so it matches the page bar's button. Claude gives only its kind.
- **How each kind moves**, when Claude doesn't move it itself:

  | Kind           | Moves on when                                                                      | Who can mark it done |
  | -------------- | ---------------------------------------------------------------------------------- | -------------------- |
  | `setup`        | Claude runs its first command before any edit (install, fetch, copy)               | Claude or Orynx      |
  | `plan`         | as today's Plan                                                                    | Claude or Orynx      |
  | `build`        | the first edit, as today                                                           | Claude or Orynx      |
  | `test`         | a command after an edit, as today                                                  | Claude or Orynx      |
  | `run`          | a port opens for this session (section 4)                                          | Orynx                |
  | `answer`       | Claude finishes with no edit                                                       | Orynx                |
  | `review`       | Claude finishes, as today                                                          | Orynx                |
  | `pull_request` | you press Create pull request, or Push changes on your own pull request (spec 031) | You                  |

- **The default steps for each intent**, used when the quick read failed or its steps broke a rule. Claude's own labels replace these words whenever it gives valid ones:

  | Intent                         | Default steps                               | Example ask                                                    |
  | ------------------------------ | ------------------------------------------- | -------------------------------------------------------------- |
  | `run`                          | Set up · Run                                | "take a pull from latest develop and start the server"         |
  | `run`, tests                   | Set up · Test                               | "run the unit tests and tell me what fails"                    |
  | `change`                       | Plan · Build · Test · Review · Pull request | "fix the login redirect loop", or a ticket chip                |
  | `change` on your PR (spec 031) | Plan · Build · Test · Review · Push         | "fix the review comments" with your open PR's chip             |
  | `answer`                       | Answer                                      | "why does the auth middleware redirect twice?" picked as Build |

- **Claude changes the steps while it works** through a new tool on the session's `orynx` MCP server (where spec 037's ticket tools already are): `set_steps({ steps, current, reason })`. It sends the whole list again: steps that are done or running keep their place, kind and label; steps still to come may be added, dropped, renamed or reordered, within the five. `current` moves the stepper to a step of a kind Claude may mark (the table above). A refused call answers with the broken rule, so Claude can send a better list, and the stepper doesn't change. Each accepted change is a row in Claude's progress: "Steps changed: the server fails on a missing env key", with the old and new lists in its details. Claude's note tells it the tool, its rules and when to use it.
- **Orynx keeps moving the stepper itself**, by kind, as today, for any step Claude doesn't move. So a session whose Claude never calls `set_steps` still shows the right step.
- **A step that's passed over is "Skipped"**, with spec 031's look. Pull request and Push are never skipped; they wait for you.
- **A follow-up** takes the stepper back to the first step after Review that isn't done, as spec 013 does, and Claude may change the steps for what you asked ("now open a PR" → adds Pull request). No second quick read.
- **The stepper never moves the page.** Five steps at 1280 px fit on one line with every label. Below 640 px only the current step shows its label; the others show their mark (number, check or dash), and their labels stay for screen readers. So it's always one line, and a change to the steps never moves anything below it.

### 4. Open ports, this session's only (Q8, Q9)

- **A tab "Ports", first, before Changes and Context** (Q9), in every Build session whose worktree is still there, with the count bubble of what listens now. The page opens on Ports for a `run` session or while something listens, else on Changes, as today. Ask sessions have no Ports tab. Windows has none (as spec 036's Terminal).
- **Only this session's ports** (Q8): a TCP port in the LISTEN state whose process is either a child of one of the session's Terminal tabs or Claude's commands, or a process whose current folder is inside the session's worktree. The second rule finds servers started any other way, such as this session's Python `Popen`. Orynx reads them with `lsof -nP -iTCP -sTCP:LISTEN` and `lsof -d cwd`, which macOS and Linux have: no new dependency. Nothing else on the computer is ever listed or stoppable from here.
- **Stop checks again on the server.** Orynx stops a process only if it is still this session's by the same rule when the request comes, never on the page's say-so.
- **How often**: every 3 seconds while the Ports tab is open, every 15 seconds for the count bubble otherwise, and never while the page is hidden. A TanStack Query with `refetchInterval`, no new server event.
- **Each row**: the port, the address (`localhost:3005`), what it is (the program's name and its command line, cut to one line, the full one in a tooltip), who started it ("Claude", "You" or "Found in the worktree") and how long it has listened. Actions:
  - **Open** for a web server, as a link to `http://` or `https://`, whichever answers. Orynx tries each once, with a 1-second timeout, when the port first appears. For anything else (5432, 6379, …) **Copy address** instead, with a known name ("PostgreSQL").
  - **Stop**: SIGTERM to the process and its children, then SIGKILL after 5 seconds, as a Terminal tab closes. No confirm for a server Claude or you started here; a confirm for one found in the worktree, which Orynx didn't start.
  - **Restart**: for a server Orynx started (section 5) it stops it and runs the same command in the same Terminal tab. A server found in the worktree has no Restart, only Stop and "Run again in Terminal", which opens a new Terminal tab with its command line typed but not run, so you check it first.
- **Empty**: "Nothing listens from this session. Servers Claude or you start here show up on their own." Loading draws the real rows' chrome, so nothing moves. An error (lsof missing, refused): "Couldn't read the ports" with Try again.
- **The session's header shows its first web address** as a link ("localhost:3005 ↗") while it listens, so the page bar is all you need to open the app.
- **Deleting a session stops its servers first**, and the Delete dialog says so: "Stops 1 server (localhost:3005)".

### 5. Claude starts servers through Orynx, not around it (Q7)

- **A new `orynx` tool: `start_server({ command, folder? })`.** Orynx runs the command in a new Terminal tab of the session, named after it ("next dev"), in the worktree or a folder inside it. You see its output live there (spec 038). The tool answers once a new port listens from that tab, within 60 seconds, with the address, or with the tab's last 40 lines when nothing listened. So the step and Claude's summary carry the real address, not a guess.
- **It always asks first** (Q7), with the approval callout (spec 012): "Claude wants to start a server: `next dev --port 3005` in apps/web" — Allow once · Always allow in this repository · Deny. "Always allow" is kept in Settings › Coding agent's allow list. A Terminal tab runs outside Claude's sandbox, as you (spec 036 Q1), so it's never allowed silently by the Commands row.
- **`stop_server({ port })`** stops a server this session started, with no ask (it can only stop what was allowed).
- **`run_in_background` stays refused**, and its refusal message now names `start_server`, so Claude has no reason to hide a server in `Popen`, `nohup` or `&`.
- **A server Claude started is yours**, as spec 036 Q3 decided: Claude finishing or Stop Claude never ends it. Deleting the session does. Quitting Orynx does, as with every Terminal tab.
- **Free port**: Claude picks the port; the tool's answer tells it if the port was taken. Orynx doesn't pick ports.

### 6. Data

- `Session` gains `intent` (`change` · `run` · `answer`), `steps` (a list of `{ kind, label, state }`, state `todo` · `running` · `done` · `skipped`) in place of `step` and `skipped`, and `branchFrom` (where the branch name's shape came from). `branch` may be null until the first edit. Stored sessions from before read as today: their `step` and `skipped` become the five-step list with today's labels.
- New activities: `reading` (the quick read: intent, base, branch and its source, or `failed`), `steps_changed` (old and new lists, Claude's reason), `branch_made` (name and source) and `server` (started, stopped or exited, with its address).
- New endpoints: `GET /api/sessions/:id/ports`, `POST /api/sessions/:id/ports/:port/stop`, `POST /api/sessions/:id/servers/:tabId/restart`. Every body is a schema in `@devhub/contracts`.
- No new dependency, token or colour.

## Goal

When I ask Orynx to run my project, it understands that, starts it without making a branch, and shows me the open ports so I can open, stop or restart them right there. When I ask for a change, the branch is named the way my repository names branches, or the way I said. The steps I see are Claude's, short, and change as soon as the work does.

## Out of scope

- **Setting a worktree up**: copying `.env.local`, certificates and other ignored files, or sharing `node_modules`, so a run starts in seconds. It's what cost the most in session `372a80e3b0347420`; it should be the next spec, with its own questions (what to copy, from where, secrets).
- Ports that aren't this session's, and stopping anything else on the computer (Q8).
- Changing what the quick read decided before Claude starts ("Did you mean…?"), or switching a session between Ask and Build after Send.
- A cheaper model for the quick read than the one you picked (Q1).
- Renaming a branch after it's made.
- Ports of containers (Docker, Podman): their listener is the VM's process, not the worktree's.
