## Assumptions

Correct these now, or the work goes ahead on them.

- **Two parts, one spec.** Part A is Settings › Skills: you write, edit and delete skills in Orynx. It is built now, on `main`. Part B puts your skills to work in sessions, through 022's `/` list in the composer (Q2). It is built after 022 (`feat/022-composer-quick-add-and-skills`) merges, on this branch, and the branch opens one pull request with both parts (Q5).
- **A skill is a `SKILL.md`, as in Claude Code.** Frontmatter, then the instructions in Markdown. Orynx keeps yours in `<DEVHUB_HOME>/plugin/skills/<folder>/SKILL.md`, as the design shows, with folders 0700 and files 0600. Each save writes a temporary file and renames it over the old one, as `settings.json` does. Orynx never writes into a repository or `~/.claude`.
- **What the file holds** (Q7): `name` is the folder name (Claude Code's rule: lowercase letters, digits and hyphens), `description` is "When to use it", and `metadata.title` is the Name you typed (the Agent Skills standard keeps extra fields under `metadata`). The Instructions box holds everything after the frontmatter. A `SKILL.md` with no title shows its folder name as its Name.
- **The folder name is made from the Name**, as the design says: lowercase, accents dropped, every run of other characters becomes one `-`, no `-` at either end, at most 64 characters. Renaming a skill moves its folder when you save. Folder names are unique among your skills. A folder under `skills/` whose name breaks this rule (say `My Skill`, made by hand) isn't listed, since no request may name it.
- **Limits.** Name at most 64 characters. "When to use it" at most 1,024 characters (Claude Code's limit), instructions at most 20,000. Orynx doesn't read a `SKILL.md` over 64 KB.
- **The tab sits after Coding agent**, as the design draws: Connections, Coding agent, Skills, Repositories, Inbox rules, Appearance. Its address is `/settings/skills`.
- **Settings keeps one frame** (Q6): the title, subtitle and local-first note stay above the tabs on every tab, as `settings.html` draws. On this tab the page bar's right side shows "4 skills in ~/.devhub/plugin" and New skill, in place of "Changes save automatically", which isn't true here: a skill saves when you press Save skill.
- **No "Let Claude pick this skill by itself" switch** (Q3). Claude reads a skill only when you name it. Claude's settings stay as 011 set them: `settingSources: []`, hooks off, no Skill tool, no plugins.
- **New `@devhub/ui` parts** (Q4), built from the design's CSS, each with a story per state and a test: `ListNav` (the skill list: items you pick, one `aria-current`), a monospace `Textarea` option for the instructions (`dh-editor`), and a `skill` kind of `SourceMark`. You add the screen to `docs/design/screens/` and the parts to `docs/design/design-system.md` with the script this branch hands you (Q4).
- **Orynx reads the folder when the tab opens**, after each change it makes, and when the server says skills changed (a new `skills.changed` event). It doesn't watch the folder. If a file changed outside Orynx while you edited it, your save wins.
- **Security.** A folder name reaches the disk only after it passes the rule above, so it can't hold `/` or `..`. The server resolves every path inside `<DEVHUB_HOME>/plugin/skills` and skips links. Logs and events carry folder names and counts, never a skill's text, title or description. The only new files are under `<DEVHUB_HOME>/plugin/skills/`. Nothing new reaches Jira, GitHub, Slack, a repository or `~/.claude`.
- **Claude gets your skill's whole file in the brief and no access to `~/.devhub`** (Part B). `~/.devhub` holds `runtime.json` with the session token, so the sandbox keeps denying it (012). Agent-runtime rule 5 holds: the composer shows `/bug-bash`, and the brief lists it.
- **New dependency** (Q12): `yaml` in `@devhub/core` reads the frontmatter, as 022 Q11 approved.
- **Tests never reach the real things.** Core tests use a temporary `DEVHUB_HOME`. E2e tests run on a hub of their own. Browser checks fake `/api` with `page.route`. Nothing reads or writes the real `~/.devhub`, `~/.claude` or a repository.
- **`docs/product/spec.md` isn't edited here.** The branch leaves you a script for its change (Settings' Skills tab), as 015 and 022 did.

## Goal

I write down once how I like a kind of work done ("Bug bash", "How we review") as a skill in Settings, and edit it whenever I learn something. When I start a session I type `/bug-bash`, and Claude gets that skill's instructions with my message. My skills live in my own folder, not in my repositories or `~/.claude`.

## Out of scope

- Automations (spec 024) and the sidebar's Automations item the design draws.
- Claude picking a skill by itself: the switch, the Skill tool, plugins and hooks (Q3).
- Skills with scripts or other files beside `SKILL.md`, and a skill's `allowed-tools`.
- Showing or editing a repository's or `~/.claude`'s skills in Settings. They stay in the composer's `/` list (022).
- Sharing skills with a team, importing them, a Markdown preview, and a skill's history.
- Watching the folder for changes made outside Orynx.
- Adding a skill with + Add context as a chip (Q2).
