# Plan: Approvals

Spec: `specs/012-approvals/spec.md`

## Before the first task

011 merged on 18 Oct 2026 (PR #19), and this branch is rebased onto that `main`. The spec's answers still fit what 011 built: `respond()` rejects, `tool-decision.ts` refuses edits in Ask before everything, `sessionNote()` says commands can't run, the stepper never reaches Test, and `ActivityStep`'s `waiting` look is unused. Each of those is a hand-over point below.

## Order of work

Today a session runs with no `Bash`: every tool call Claude Code doesn't allow by itself comes to `decideToolUse()`, which only allows or refuses, and the adapter answers the SDK at once. This spec adds the third answer, "ask", and everything from that pause to the click: the decision tables, the sandbox the allowed command runs in, the waiting state, the route that carries the answer, the callout, and the allow list in Settings.

1. **Contracts first** (tasks 1 to 3).
   - **The command reader lives in `@devhub/contracts`** (`commands.ts`), next to `jiraCloudHost` and `RepositoryPathSchema`: a rule the form and the server must agree on, with no dependency (Q3). It splits a command into parts at `&&`, `||`, `;` and `|` (quotes and escapes minded), says why a command always asks (`network`, `delete_outside`, `unsandboxed`) or is refused (`push`), and gives the entry Always allow would save (Q4). `AllowedCommandSchema` refines on it, so Settings' form and `PATCH /api/preferences` refuse the same entries with the same reasons. It's string work only; matching against the worktree and the allow list stays in core.
   - Preferences gain `allowedCommands` and the change gains `allowCommand` and `disallowCommand`, one entry each, so two quick changes can't undo each other.
   - A session gains `approvals`: the calls still waiting, in order. Each is structured data (the command, Claude's description, why it always asks, the entry Always allow would save; or the path, whether it creates the file, and the change as lines with how many more there are). The activities gain `waiting`, `command`, `denied` and `no_commands`, and `refused` gains the reasons `push` and `background`. The route is `POST /api/sessions/:id/approvals/:approvalId` with `{ decision }`.
2. **Pure pieces of core** (tasks 4 to 7), each a table before anything waits.
   - The preferences service reads and saves `agent.allowedCommands`, adding without duplicates and removing by entry.
   - `command-decision.ts`: every mode against every kind of command (plain, on the list, several parts with filters, `cd`, substitution, network, delete outside, unsandboxed, push, background) gives allow, ask (with why and the Always allow entry, Q1) or refuse (Q7).
   - `tool-decision.ts` learns to ask: `Bash` goes to the command decision, and an edit in Ask before everything asks with a preview of the change (`edit-preview.ts`: the old and new text from the tool's input, numbered from where the old text sits in the worktree's file, at most 20 lines, then how many more; a new file as added lines, Q9). Outside the worktree still refuses.
   - `sandbox.ts`: whether Claude Code's sandbox can run here (macOS with `sandbox-exec`, Linux with `bubblewrap` and `socat`, never Windows) and the settings a session passes: enabled, `failIfUnavailable: true` so nothing runs unsandboxed by surprise, `autoAllowBashIfSandboxed: false` so every command still comes to Orynx, writes only in the worktree and the temporary folder, no reads under `DEVHUB_HOME` or the keychain folder, and no network (Q2).
3. **The adapter waits** (task 8). `canUseTool` parks an "ask" until `respond()` answers it, Stop denies every parked call before interrupting, and the SDK's own abort signal denies too. The adapter emits an `approval` event for the page and a `command` work when a command is allowed, so "Running a command" shows while it runs. An allowed always-ask command gets `dangerouslyDisableSandbox: true` in `updatedInput`, so it runs outside the sandbox that once. `startSession` takes a `permissions()` reader instead of a value, so each call sees Settings as they are then. Where the sandbox can't run, the session gets no `Bash` and a `no_commands` event. The fake SDK answers an ask the way Claude Code does.
4. **Folding** (task 9). The message reader also turns a `Bash` result into `command` work (so a command Claude Code allowed by itself still shows), and `progress.ts` groups commands like edits, replaces a `waiting` step with `command` or `denied` when answered, and moves the stepper to Test on the first command after the first edit (AC-17).
5. **The session service** (task 10). Approvals live in the record with their answers and who gave them; the session is Needs you while any waits; `respond()` handles Allow once, Always allow (save the entry first, then allow; a failed save decides nothing), Deny, a late answer, and an unknown approval; Stop, Discard and `close()` answer the rest as stopped or interrupted. The note for Claude's system prompt changes to Q8g. The log names kinds and answers only.
6. **Routes, store and host** (tasks 11 to 13). The approval route (204; 404; 409 answered; 503 when the list can't be saved), the file store reading old sessions without `approvals`, and `apps/server`'s `DEVHUB_SANDBOX` (`required` by default, `assume` for the e2e run, whose fake Claude Code has no sandbox; the SDK's `failIfUnavailable` still guards a real one).
7. **The e2e fake** (task 14). The fake Claude Code asks `can_use_tool` for a `Bash` call and plays what the answer allows, picked by the ticket's title. A probe records what the pinned SDK sends for `sandbox` and `autoAllowBashIfSandboxed`, as 011 did for its flags.
8. **api-client** (task 15): `respondToApproval`; preferences changes already flow through.
9. **`@devhub/ui`** (task 16). `Callout` gains a `code` block for the command (mono, wrapped, scrolling past 12 lines), as `design-system.md` draws it, with its story and test.
10. **The app** (tasks 17 to 20): the words (step words for the new kinds, the callout's titles, why-lines and errors, the pill), `ApprovalCallout` (the first waiting approval, Always allow only when the server offers an entry, busy and error states, 409 treated as answered, focus rules, the edit preview in `DiffView`), the Session screen wiring, and Settings' "Allowed commands" (rows with Remove, the form with react-hook-form and the contract's schema, the empty line, focus after Remove).
11. **e2e, docs and the browser** (tasks 21 to 24), the user's real run with the real sandbox (task 25, Q10), and `/review`.
