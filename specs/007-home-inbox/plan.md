# Plan: Home inbox

Spec: `specs/007-home-inbox/spec.md`

## Order of work

The work splits in two at 006. Everything up to task 15 needs nothing from 006 and is built now, while another session builds 006. Tasks 16 to 21 build the Home screen from 006's `AttentionList`, `AttentionRow`, `Panel` and `Skeleton`, and start only after 006 merges and this branch moves onto `main`.

1. **Contracts first** (task 1). The inbox's shape (`GET /api/inbox`), its two actions (`POST /api/inbox/refresh`, `DELETE /api/inbox/cache`) and the `inbox.changed` event. The server sends data, never words that change with the clock: a reason's kind, when the wait started, and when a tool last synced. The app writes the pill, the wait and "Synced 2 min ago", so they move on each minute without a request (AC-13). Static words that never change with time (a tool's own problem message from specs 003 and 004) may come from the server. The sub line is data too (key, status, repository, author), so all of Home's wording lives in one place in the app.
2. **The cache** (task 2). better-sqlite3 and drizzle-orm, as `docs/architecture.md` plans. Two tables: one row per synced record (ticket or pull request) as JSON, checked with zod on the way out, and one row per tool with its last sync and problem. The schema version lives in `PRAGMA user_version`. A file that isn't a database, or holds another version, is deleted and made again (AC-29). Tests use `:memory:`, and the host passes `<DEVHUB_HOME>/cache.db` (mode 0600).
3. **The reads** (tasks 3 and 4), each in its tool's `client.ts`, the only file that talks to the network:
   - Jira: `POST /rest/api/3/search/jql` (the old `/search` is gone) with the fields the rows need, plus `GET /rest/api/3/priority/search` for the site's priority order (Q2f). Mapped by status category in `map.ts`.
   - GitHub: one GraphQL query through octokit's `graphql`, with two searches (review requests to you by name, and your own pull requests) carrying the review-request events, the latest commit's check rollup and the review threads. `map.ts` turns them into records.
4. **The rules** (task 5). A pure `rules.ts` turns records, the inbox rules and the waiting sessions into rows: one row per ticket or pull request, the most pressing reason (Q4), the tab, the target link, sorted by wait.
5. **The sync** (tasks 6 and 7). Each connection gets one call that hands out its working credentials, with a problem when it can't. The sync service runs one sync at a time (a second caller joins it), syncs the connected tools side by side, writes each one's records or its problem, and publishes `inbox.changed` when it ends. A sync that ends after a Disconnect writes nothing.
6. **Routes and the schedule** (tasks 8 and 9). The three routes, and an `autoSync` option that hosts turn on: a sync at start, every 2 minutes while a page has the event stream open, and at once when a tool connects. A disconnect removes that tool's records. `autoSync` is off by default, so no existing test reaches Jira or GitHub by surprise (the `gh` option works the same way). The event bus learns to count open pages separately from its own listeners.
7. **The host and the leak test** (task 10). `apps/server` opens the cache file and turns `autoSync` on. A test runs the real hub at trace level through a sync and searches the log and `cache.db` for the tokens and any description or comment text (AC-28).
8. **api-client and live updates** (task 11). `inbox()`, `refreshInbox()` and `clearInboxCache()`, their query options, and the events: `inbox.changed`, `settings.changed` (the rules apply on read) and `status.changed` (a connection changed) all invalidate the inbox.
9. **The words** (task 12). Pure functions in `packages/app/src/features/home/` for each pill (text, spoken text, tone), each sub line, each action, the page bar's sync line and each tool's line. Tested on their own with a fixed clock, so the screen tasks only lay things out.
10. **Two places that already exist** (tasks 13 and 14): the sidebar's Home count, and Clear cache on Settings › Inbox rules.
11. **Docs** (task 15). Architecture (the cache is decided, `cache.db`, the inbox routes) and a `learn/` page on how the inbox syncs.
12. **After 006 merges** (tasks 16 to 21): move onto `main`, then the panel and tabs, the states, the page bar, focus when a row goes, an e2e run, and the browser check.
