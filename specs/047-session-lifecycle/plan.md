# Plan: Session lifecycle

Spec: `specs/047-session-lifecycle/spec.md`

## Order of work

1. **A. Another session (Tasks 1–5).** It comes first because B's Fix shows the same choice and sends the same `another: true`. Contracts → `composeNow` (`session-service.ts:1427`) → the follow-up rule and `sessionsByTicket` (`ticket-sessions.ts`) → the composer's callout (`home-composer.tsx:42`) → its e2e.
2. **B. Fix on Home (Tasks 6–10).** The inbox learns a fork from GitHub (`isCrossRepository`). The server picks a folder by the pull request's origin when the start names none. `rowAction` (`inbox-words.ts:109`) gets a Fix kind, and the row's button starts the session. Its "existing" and "can't start" answers reuse A's callout and Send's line, so the composer's answer moves into the composer store (UI-only state, zustand).
3. **C. After the merge (Tasks 11–16).** First the two new states, since adding them to `SessionStateSchema` breaks every exhaustive map at once (`session-item.tsx`, `agent-chip.tsx`, `session-header.tsx:49`, `session-filters.ts:21`). The typecheck finds them all, so they go in one task. Then a small GitHub call for a pull request's state and head, then the "nothing would be lost" check in `branch-git.ts`, then the watch that runs with the inbox's sync (`inbox-schedule.ts:44`). After that, merged sessions stop counting as live and their follow-up box changes. Last, the e2e on the pull-requests hub.
4. **D. Cleanup schedule (Tasks 17–22).** Contracts first (the preference, the bell's kind, `GET /api/storage`), then the pure choice of which sessions go (reusing C's check), then the hourly schedule and its notification, then the api-client, the Storage section in Settings › Coding agent, and its e2e.
5. **E. Turns and cost (Tasks 23–25).** The SDK's `result` (`sdk-messages.ts:66`) becomes a `usage` agent event. The session adds up turns and keeps the latest cost, including after Stop (`heard()`, `session-service.ts:570`). The progress line shows them, then the e2e.
6. **Task 26: STOP and run /review.**
