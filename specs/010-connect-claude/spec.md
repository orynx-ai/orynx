# Connect Claude

Status: approved
Roadmap: Phase 3 — Claude sessions, built early (the user's call, 2026-10-17)

## Assumptions

Correct these now, or the work goes ahead on them.

- **Build order.** On 2026-10-17 the user set the order after 004: Settings (005) and the components (006), then Claude (010) and Home (007), with Slack (016) still near the end. 005 to 008 have merged since, and 009 is being built in another session; this spec doesn't depend on 009. Spec numbers stay as they were, so "moved to 007" in specs 003 and 004 still points to the right spec. The roadmap's 010 and 011 lines change to match Q1.
- **There is nothing to connect inside DevHub.** Claude Code owns the login ("Already done if Claude Code works on your laptop", product spec). DevHub only checks it. There's no Connect or Disconnect button, nothing in `settings.json` or the keychain, and DevHub never runs `claude auth login`, `claude auth logout` or `/login`.
- **How DevHub checks.** It runs the Claude Code program that ships inside `@anthropic-ai/claude-agent-sdk` with `auth status --json`. That reads the login on this computer and prints `{ "loggedIn": true, "authMethod": …, "apiProvider": …, "email": …, "orgName": … }`. It sends no prompt and uses no quota. It took 0.16 s on this Mac and exits 1 when signed out (Q2). DevHub gives it at most 10 seconds. This spec adds the package, which `docs/architecture.md` already lists as planned.
- **What "signed in" proves.** A login exists on this computer. `auth status` doesn't ask Claude's servers, so whether they still accept the login shows only when the first session starts (011).
- **When DevHub checks.** On the first status request after start, then at most every 2 minutes, the way Jira and GitHub are checked (`checked-status.ts`). Check again checks at once. A changed answer reaches every open page through `status.changed`.
- **The program gets a short environment, not DevHub's.** Only `HOME`, `USER`, `LOGNAME`, `PATH`, `SHELL`, `TMPDIR`, `LANG` and `LC_*` get through, plus Claude's own settings (`CLAUDE_*` and `ANTHROPIC_*`), the cloud logins Claude Code can use (`AWS_*`, `GOOGLE_*`, `CLOUD_ML_REGION`), and proxy and certificate settings (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` in either case, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`). No `DEVHUB_*` variable gets through, so no `.env` token and no session token reaches it. Spec 011 uses the same list for sessions. Of `CLAUDE_*`, the variables a Claude Code session sets for its own programs stay out, such as `CLAUDE_CODE_SESSION_ID` and `CLAUDE_CODE_MESSAGING_TOKEN`: Orynx started from a Claude Code terminal has them, but what Orynx starts isn't part of that session (found while building; the user's call, 18 Oct 2026). For the login check DevHub also sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`: the pinned build's `auth status` records an analytics event otherwise (found while building, 18 Oct 2026). It runs in its own folder, `<DEVHUB_HOME>/claude-check` (mode 0700), so neither a repository's `.claude` settings nor ones another account leaves in a shared `/tmp` change its answer (the review, 18 Oct 2026).
- **The account stays in memory.** The email and organisation are read for the Settings card on each check. They are never saved or logged.
- **The Coding agent tab already exists.** Spec 005 built it at `/settings/coding-agent` with the permission modes, and left the agent cards to this spec (spec 005, Q1). This spec adds the Claude card and the "More agents" card above the modes, as the design draws them. The modes don't change.
- **The sidebar footer keeps its two lines.** It says "Claude connected · runs locally" when Claude Code is signed in, and "Claude not connected · runs locally" otherwise, including when the check fails.
- **Tests never run the real Claude Code.** Core tests and e2e get a fake program, the way spec 004 faked gh. If `createServer()` is given no program, it reports Claude as not connected and starts nothing.
- **Install size.** The SDK installs the Claude Code build for your platform only. On this Mac that's about 270 MB in `node_modules`, so the first `pnpm install` after this spec takes longer.

## Goal

Before I hand Claude a ticket, I want DevHub to tell me whether Claude is ready. If Claude Code already works on my laptop, DevHub uses the same company login with nothing to set up. If it doesn't, DevHub says how to sign in and lets me check again without restarting.

## Out of scope

- Starting, running, approving or stopping a session, and the adapter's session methods (011 and 012, Q1).
- Signing in to or out of Claude from DevHub.
- Changing the permission modes on the same tab (005 built them) and the allow list behind them (012).
- The agent picker in the composer (015), and any agent other than Claude.
- Asking Claude's servers whether the login still works, and showing quota, usage or the model.
- Using a `claude` found on the PATH instead of the one in the SDK (Q2c).
