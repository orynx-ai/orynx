# Plan: Connect Claude

Spec: `specs/010-connect-claude/spec.md`

## Order of work

Everything around the check is already there: `GET /api/status` carries `agent: { id: 'claude', connected }`, the sidebar footer already reads it, `status.changed` already refreshes it in every tab, and 005 built the Coding agent tab with the permission modes. Today `status-service.ts` answers `connected: false` for good. This spec replaces that answer with a real check and adds the two cards above the modes.

1. **Contracts first** (task 1). `ClaudeLoginSchema` is what the card needs: `signed_in` with how (`claude_ai`, `api_key`, `bedrock`, `vertex`, `other`), the email and the organisation (each nullable), or `signed_out`, or `error`. It carries no reason and no exit code: those go to the terminal only (AC-6). It's served at `GET /api/claude/login`. Check again is `POST /api/claude/login/check`, which checks now and answers with the result. `StatusSchema` doesn't change: the footer needs only `connected`, so the email never travels in `/api/status`.
2. **The short environment** (task 2). `agent-environment.ts` is a pure function from an environment to the allow-listed one (spec Assumptions, AC-10). It's its own file because 011 starts sessions with the same list.
3. **The program** (tasks 3 and 4). `claude-code.ts` is the only file that starts Claude Code, the way `gh.ts` is for gh. It finds the program inside the SDK's platform package without running it, then runs it with exactly `auth status --json`, the short environment, a 10-second `SIGKILL` timeout and a small output limit. It reads stdout with a zod schema into a login or a problem: `missing`, `failed` with the exit code, `unreadable` or `timeout`. Tests use a fake program, as `fake-gh.ts` does: a real script in a temp folder that records its arguments and its environment.
4. **The check's rhythm** (tasks 5 and 6). `createCheckedStatus` learns to hold any answer, not only `IntegrationStatus`, and gains `checkNow()` for Check again: it starts a check unless one is running, and then it shares that one (AC-7). Jira and GitHub keep their behaviour and their tests. `claude-login.ts` puts the program behind it: the first request checks, later requests within 2 minutes reuse the answer, and after 2 minutes a request answers at once while a re-check runs. A changed answer publishes `status.changed`. A problem logs its kind and exit code, never the output, the email or the organisation (AC-6, AC-11).
5. **Routes and wiring** (tasks 7 and 8). Two routes, `createServer({ claudeCode })`, and the status line from the same check. Left out, the program is never found, so no test can start the real Claude Code (AC-12). A leak test runs signed in, signed out and failing at `LOG_LEVEL=trace` with the event stream open (AC-11).
6. **The host and e2e** (task 9). `apps/server` passes the SDK's program. The e2e run needs a fake one. gh was found on PATH, but Claude Code isn't on PATH, so a new setting `DEVHUB_CLAUDE_CODE` names the program to run (empty means the SDK's own). It goes in `config.ts` and `.env.example`, and `playwright.config.ts` points it at `e2e/fake-claude/claude`.
7. **api-client and live updates** (task 10). `claudeLogin()`, `checkClaudeLogin()` and their query options. `status.changed` refreshes the login too.
8. **`Card` in `@devhub/ui`** (task 11), as Q4 answered: plain, `selected` and `placeholder` looks, with stories, a test and its design-map row.
9. **The cards** (tasks 12 and 13). `ClaudeCard` with its four states (Q3, Q5), and Check again keeping focus and the card's size (AC-7). Then the cards row above the modes in `CodingAgentPanel`, with "More agents".
10. **e2e, docs and the real browser** (tasks 14 to 16). Then the user checks their real login (Q7), and `/review`.
