# Architecture

DevHub has two halves, both on the developer's laptop: a React web app and a Node server, which the spec calls "the hub". The web app asks the hub for data and gets live updates back. The hub calls Jira, GitHub, Slack and Claude with the user's own logins. There is no DevHub cloud.

```
 browser (or desktop window)                 laptop: local server (127.0.0.1:4317)
┌──────────────────────────────┐   HTTP    ┌───────────────────────────────────────┐
│ apps/web  ─ mounts ─┐        │  + SSE    │ apps/server ─ hosts ─┐                │
│                     ▼        │ ────────▶ │                      ▼                │
│  @devhub/app (screens,       │           │  @devhub/core (Fastify routes,        │──▶ Jira / GitHub / Slack
│   routes, zustand, queries)  │ ◀──────── │   integrations, agent runtime,        │──▶ Claude Agent SDK
│  @devhub/ui (design system)  │  events   │   storage in ~/.devhub)               │──▶ git worktrees
│  @devhub/api-client (axios)  │           │                                       │
└──────────────┬───────────────┘           └──────────────────┬────────────────────┘
               └──────── both import @devhub/contracts (zod) ─┘
```

## Packages

Each package's source is TypeScript that the consuming bundler or `tsx` compiles directly. There is no per-package build step: `exports` points at `src/`. Only the two hosts in `apps/` build.

| Package                            | What it owns                                                                                                                              | May import (internal)     | Key libraries                                                                                               |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `@devhub/contracts`                | zod schemas and inferred types for every HTTP body and server event, plus API paths                                                       | nothing                   | zod                                                                                                         |
| `@devhub/api-client`               | axios instance, one typed function per endpoint, TanStack Query `queryOptions`, the event stream                                          | contracts                 | axios, @tanstack/react-query                                                                                |
| `@devhub/ui`                       | design tokens, Tailwind theme, shadcn-based components, Storybook                                                                         | nothing                   | react, radix-ui, cva, tailwind-merge, @hugeicons/react, @hugeicons/core-free-icons, lucide-react (fallback) |
| `@devhub/app`                      | the product UI: shell, routes, features, zustand stores, the `Platform` interface                                                         | contracts, api-client, ui | react, @tanstack/react-router, @tanstack/react-query, zustand, react-hook-form, @hugeicons/core-free-icons  |
| `@devhub/core`                     | `createServer()`: Fastify plugins and routes, the event bus, integrations, the agent runtime, storage                                     | contracts                 | fastify, fastify-type-provider-zod                                                                          |
| `@devhub/web` (`apps/web`)         | the browser host: Vite, `index.html`, the web `Platform`, the token meta tag                                                              | app, ui, api-client       | vite, @tailwindcss/vite                                                                                     |
| `@devhub/server` (`apps/server`)   | the Node host: env config, data dir, session token, static files, `listen()`                                                              | core, contracts           | @fastify/static, tsdown                                                                                     |
| `@devhub/desktop` (`apps/desktop`) | the desktop host: Electron starts `apps/server`'s bundle on a free port and opens its page in a window, and checks for updates (spec 027) | no other @devhub package  | electron, electron-builder, electron-updater, tsdown                                                        |

`pnpm gate boundaries` enforces the "may import" column, and blocks Node built-ins and server libraries in browser packages.

## Runtime

- **Ports.** The server always binds `127.0.0.1:4317` (`DEVHUB_PORT`). In `pnpm dev`, Vite serves the web app on `localhost:4318` (`DEVHUB_WEB_PORT`) and proxies `/api` to the server. In `pnpm start`, the server also serves the built web app, so there is one port.
- **Session token.** On every start, the server makes a random token and writes `{ port, token, pid }` to `<DEVHUB_HOME>/runtime.json` (mode 0600). The page carries it in `<meta name="devhub-token">`: in production the server injects it, and in dev a small Vite plugin reads `runtime.json`. Every `/api` request sends `x-devhub-token`. `EventSource` cannot set headers, so the event stream takes `?token=`.
- **Host check.** The server rejects requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`. This blocks DNS-rebinding pages from reading the token. See `learn/local-security.md`.
- **Live updates.** `GET /api/events` is a server-sent event stream of the `ServerEvent` union from contracts. The app turns events into TanStack Query invalidations; it never patches stores by hand.
- **Data.** Everything lives under `DEVHUB_HOME`, which defaults to `~/.devhub`: `runtime.json`, `settings.json` (the Jira site and email, the way GitHub is connected, and Settings' own values from spec 005: the permission mode, the inbox rules and the folders with their Jira projects, and the editor from spec 013; Tickets' choice of project and sprint, spec 020, which disconnecting Jira or connecting another site clears; never a token), `cache.db` (SQLite: the inbox's last sync, spec 007, and Tickets' sprint, spec 008, titles and metadata only, made again when it can't be read), `sessions/`, `worktrees/`. `createServer()` takes the settings store from the host, like the keychain; tests use memory or a temporary `DEVHUB_HOME`.
- **The inbox.** `GET /api/inbox` answers from `cache.db` at once and applies the inbox rules as it reads. `apps/server` passes `autoSync: true`, so the hub syncs Jira and GitHub at start, every 2 minutes while a page has the event stream open, and when a tool connects; `POST /api/inbox/refresh` syncs on demand and `DELETE /api/inbox/cache` is Clear cache. Without `autoSync` (tests), only those two sync. See `learn/the-inbox.md`.
- **Tickets.** `GET /api/tickets` answers from `cache.db` with the sprint and its tickets, each with its newest session joined. The sprint is read in the inbox's sync, side by side with the other reads, in its own part of the cache: the active sprint holding most of your issues, its board's columns (for In review, by status id) and up to 300 issues in rank order. Spec 020 lets you pick the sprint instead (`PUT /api/tickets/choice`, kept in `settings.json`): a project's current sprint, one held sprint, or the tickets in no sprint; the cache keeps the choice each sprint was read for, so a new pick reads as syncing until its first pass. `inbox.changed` refreshes it. See `learn/the-tickets-board.md`.
- **Folder picker.** Choose folder (spec 020) asks the server to open the computer's own picker: `osascript` on macOS, `zenity` or `kdialog` on Linux, found on the shell's `PATH` like `gh`, run with a fixed command (no shell, nothing the page sent), one at a time, closed after 10 minutes. Windows has none yet. See `learn/settings-and-folders.md`.
- **Search.** `GET /api/search` answers from `cache.db` and the session store, never from Jira or GitHub: the assigned issues and every open pull request the inbox's sync keeps (with no inbox rules), the sprint, and every session, each group in its own order. The browser asks once when ⌘K first opens it and matches as you type; `inbox.changed`, `status.changed` and `sessions.changed` refresh it. The dialog is `@devhub/ui`'s `Dialog` (Radix Dialog from `radix-ui`, without its overlay) around `SearchPalette`. See `learn/search.md`.
- **Settings.** `apps/server/src/config.ts` reads the shell's variables and the repo-root `.env` (with `node:util` `parseEnv`); the shell wins. Every key is in `.env.example`.
- **Tokens.** Jira, GitHub and Slack tokens live in the OS keychain (service "DevHub", one account per tool) through `app.tokens`, which `createServer()` builds from the keychain the host passes. The native library loads on the first token call, never at start. `.env` holds tokens only when the user sets `DEVHUB_TOKENS_FROM_ENV=true`. `DEVHUB_KEYCHAIN=memory` keeps them in memory instead; the e2e run uses it so it never touches a real keychain. See `learn/tokens-and-keychain.md`.
- **Commands in a session.** Claude runs commands only inside Claude Code's own sandbox (Seatbelt on macOS; bubblewrap and socat on Linux), which `createServer()` sets for each session from `agent.sandbox`: writes only in the worktree and the temporary folder, no reads under `DEVHUB_HOME` but the worktree, no network. `apps/server` checks that the sandbox can run (`sandboxAvailable()`, or `DEVHUB_SANDBOX=assume` for the e2e run's fake Claude Code); without it, sessions get no commands. What runs, asks or is refused is decided from contracts' command reader, which Settings' allow list shares (`learn/sessions-and-worktrees.md`).
- **The composer's start.** `POST /api/sessions` takes Ship's `{ ticketKey, repositoryId? }` or the composer's `{ message, repositoryId?, context }` (spec 015), with a 4 MiB body limit on that route alone. A composer start reads its chips before it makes anything: a ticket's comments and links from Jira (`issueContext()`), and a pull request's details by GraphQL and its diff by REST from GitHub (`pullContext()`, `pullDiff()`). It writes nothing to either. A chip that fails answers `context_failed` with its place. Fastify's own 4xx refusals are answered with their status and `bad_request`. See `learn/composer-and-context.md`.
- **A session's changes and follow-ups.** `GET /api/sessions/:id/changes` lists what differs in the worktree from the commit the branch started from, and `GET /api/sessions/:id/changes/diff?path=` gives one listed file's diff, both read with read-only git (`diff.autoRefreshIndex=false`, no hooks, 10-second limit). `session.files.changed { sessionId }` says when to read them again, at most once a second. `POST /api/sessions/:id/messages` sends Claude a follow-up: into the running Claude Code, or by resuming its own session (the Agent SDK's `resume`) once it has finished or stopped. The Session screen's Open in is a `vscode://` or `cursor://` link, the editor Settings › Coding agent picks (`agent.editor` in `settings.json`). See `learn/sessions-and-worktrees.md`.
- **A session's pull request.** `POST /api/sessions/:id/pull-request/draft` asks Claude for a title and description through the adapter's `write()`: no tools, nothing saved, an empty folder as its working folder, 60 seconds. It changes nothing. `POST /api/sessions/:id/pull-request` commits what isn't committed (your git identity, never a made-up one), pushes the session's branch to `origin` under its own name without force, and opens the PR with `@octokit/rest` and the GitHub connection's token, only on that press. `POST /api/sessions/:id/push/draft` and `/push` do the same for changes after it opens. The repository's hooks never run, and a new file that looks like a secret stops the commit. See `learn/sessions-and-worktrees.md`.
- **Certificates.** At start, the server trusts the OS's certificates as well as Node's own (`apps/server/src/system-certificates.ts`, what `--use-system-ca` does), so a company TLS proxy doesn't break calls to Jira, GitHub or Slack. See `learn/connecting-jira.md`.

## Porting to a desktop app

The split exists so a desktop app is a third host, not a rewrite:

- `apps/desktop` (Electron) main process: `createServer()` from `@devhub/core` on a random 127.0.0.1 port, with the same token handshake.
- Renderer: mounts `<DevhubApp>` from `@devhub/app` with `createHashHistory()` and a desktop `Platform` (native folder and file dialogs, `shell.openExternal`, notifications).
- Nothing in `app`, `ui`, `api-client` or `contracts` changes. Anything that differs between the browser and desktop goes through `Platform` (`packages/app/src/platform.tsx`), never `if (isElectron)`.
- Native modules (better-sqlite3, keyring) need `electron-rebuild`; keep them inside `core` so only the main process loads them.

## Decisions

| Decision                                                       | Why                                                                                                                    |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Fastify, not Express                                           | The spec names it, it is schema-first with zod type inference, and `app.inject()` tests routes without opening a port. |
| JIT internal packages (`exports` → `src/*.ts`)                 | No build watch loops in dev, and go-to-definition lands in source. Only hosts bundle.                                  |
| Separate Vite port in dev                                      | Standard Vite HMR with no server middleware coupling; the proxy keeps one origin for the browser.                      |
| Self-hosted fonts                                              | Local-first: the page loads nothing from the internet.                                                                 |
| `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` on | Agents write faster than people review; the compiler catches the gaps.                                                 |
