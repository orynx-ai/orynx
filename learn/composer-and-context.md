# The composer: your words and context, as Claude's brief

Home's composer starts a Claude session from what you type, without a ticket if you like. You add context with the + button: a folder, Jira tickets, pull requests and files from this computer. You name a skill by typing `/`. What Claude gets is exactly what the composer shows: your message, then each chip in the order you added it, then each skill you named, and nothing else. Spec 015 built it. Spec 022 let it take several tickets, files by path and skills, and made it the one place a session starts from the page: Home's rows, Ship on Tickets and the ticket dialog all add their ticket here.

## The path of one Send

```
HomeComposer                                        (the page: features/home/components/home-composer.tsx)
  └─ POST /api/sessions { message, repositoryId?, context: [jira | pull_request | file] }   up to 4 MiB
       └─ session-service.ts start() → composeNow()   checks before anything exists:
            a live session on the first ticket? → existing; the page says so, with Open session (Q9)
            Claude Code signed in?  fewer than 3 working?  the folder (compose.ts chooseFolder, Q7)?
            context-reader.ts: every chip at once
              jira          client.issueContext()   GET /rest/api/3/issue/{key} with comments and links
              pull_request  client.pullContext()    one GraphQL query: title, body, branches, failed
                                                    checks, unresolved threads, changed files
                            client.pullDiff()       GET /repos/{o}/{r}/pulls/{n} as a diff; 406 = too large
              file          file-paths.ts readableFile()   a file this process can read? then its real
                                                    path; its contents are never read
            a chip that failed → context_failed { chip, problem }; nothing is created
            skills-service.ts named()   each /name in the message that's a skill here, at most 5
            compose.ts composerPlan(): the title, the branch name, the brief, the brief step, what Claude may read
       ← started { sessionId }; the page clears its draft and opens /sessions/<id>
       └─ run() takes that plan from memory instead of reading the ticket, then as 011:
            the worktree on feat/<KEY> or feat/<slug>, brief.md, the brief step, Claude
```

## Several tickets (spec 022, Q2)

The first ticket you add is the session's ticket. Its key names the branch (`feat/PROJ-1423`), its summary is the title, it's the session's source and Ticket tab, its project picks the folder (Q7), and its live session stops Send. Every other ticket is context only: Claude gets the same text for it, and the brief step lists it after the first (`tickets` in the `brief` step). `ticketKeyOf()` on the server and `firstTicket()` in the page both take the first `jira` chip, so removing it makes the next one the session's ticket in both places. With several tickets the box reads "What should Claude do with these 3 tickets?".

## What the brief holds

`brief.ts` `composerBrief()` writes your message first, then each chip under its own title, then each skill:

| Part         | Title                                                             | Body                                                                                                                                                                                                           |
| ------------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jira ticket  | `Jira ticket PROJ-1423 (Story): Add bulk archive`                 | The description as Markdown, then `## Comments` (the last 20) and `## Linked issues`. Every ticket gets this, the first or not                                                                                 |
| Pull request | `Pull request acme/web-app #2836: Lazy-load the people directory` | The branches, the description, `## Failing checks`, `## Unresolved review comments`, then `## Diff`: the first 2,000 lines, then every file's counts; or the counts alone when GitHub finds the diff too large |
| File         | `File ~/notes/plan.pdf`                                           | "The user added this file from their computer. Read it at /Users/you/notes/plan.pdf. It's outside your worktree: you can read it, not change it." The path is the real one, every symlink followed             |
| Skill        | `Skill /review`                                                   | "The user asked for this skill with /review. Follow it for this task.", then where its folder is, then the skill's file without its frontmatter (at most 256 KB)                                               |

The same text is saved as the session's `brief.md` (0600). Claude's note says "Make the change the ticket asks for." only when the ticket alone is the brief. With your own words, it says "Do what the user asks in the brief." (Q8c). A follow-up keeps whichever the brief step shows.

A session with no ticket gets its title from your message's first line (80 characters, cut on a word), and its branch from the title's first five words in lower-case ASCII (`feat/add-a-csv-export-to`, or `feat/task` when nothing is left). Its `source` is null, so the Session screen says Sessions / its title and has no Ticket tab, and its inbox row leads with Orynx's own mark (`SourceMark source="orynx"`). Its pull request (spec 014) has no key in front of its title and no Jira line: `pull-requests.ts` gives such a session no ticket key, so the draft's prompt says "The task, as Claude got it", `draftInstructionsFor()` asks Claude for no key, and when Claude can't draft, the title is the session's own (AC-34).

## Files by path (spec 022, B)

A file chip holds a path, never the file's text. A browser never tells a page a file's path, so File from this computer asks the local server to open the computer's own file picker (`POST /api/file-picker`), as Choose folder does (`learn/settings-and-folders.md`). `createFilePicker()` in `folder-picker.ts` runs `osascript -l JavaScript` on macOS, which answers the paths as JSON, so a name with a line break stays one file. On Linux it runs `zenity --file-selection --multiple` or `kdialog --getopenfilename --multiple`, which answer one path a line. Several files come back at once, with `~` for your home folder, or null on Cancel.

- **No picker.** Where none can open, the route answers 503 `picker_unavailable`, and the page opens Add a file (`add-file-dialog.tsx`): a Path field (react-hook-form, from `/` or `~/`) whose path `POST /api/files/check` looks for. The server answers `found` with the path as it shows it, or `not_found`, and reads nothing.
- **No type or size.** Claude Code's own Read tool reads text, images, PDFs and notebooks, so Orynx checks neither. A 2 GB video is one short path.
- **Secrets stay out.** A name that looks like a secret (`.env`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`) is never a chip: the page says "id_rsa looks like a secret, so Claude doesn't get it.", and the contract refuses it too. The rule is `looksLikeSecret()` in `contracts/src/secret-names.ts`, the same one that stops 014's commit.
- **Checked again at Send.** `context-reader.ts` asks `readableFile()` whether a file this process can read is still there, and takes its real path. A file moved away fails as `not_found`, and the line under the box says "Orynx can't find ~/notes/plan.pdf." with nothing made.
- **What Claude may read.** The real paths go into the session's `reads`, which the tool decision allows for read tools only. Claude can read exactly those files, wherever they are, and never change them (below).

## Skills on `/` (spec 022, G)

`/` at the start of the box, or after a space or a new line, opens a list of skills under the box, as Claude Code's terminal does. The list comes from `GET /api/skills?repositoryId=` for the folder the picker shows, or yours alone without one. `skills-reader.ts` reads:

- the folder's `.claude/skills/<name>/SKILL.md` and `.claude/commands/**/*.md` (three folders deep at most; `git/commit.md` is `/git:commit`);
- then the same under `~/.claude`, which the list calls Yours.

Each name and description comes from the file's YAML frontmatter, read with `yaml` from its first 64 KB. A skill with no `name` takes its folder's name. A file that can't be read or whose frontmatter won't parse is left out, and so is a name `/` can't be typed with. A folder's skill wins over yours with the same name. Nothing else is read for the list, and nothing is written. The page asks only once `/` is typed, keeps the answer per folder while it's open (`skillsQueryOptions`, `staleTime: Infinity`), and asks again for another folder.

In the page, `useSkillSuggestions()` (`skill-suggestions.tsx`) drives `@devhub/ui`'s `SuggestionList`. Focus stays in the box, which points at the list with `aria-controls` and at the active row with `aria-activedescendant`. Typing filters, the arrow keys move, and Enter, Tab or a click puts `/name ` in the box. While the list offers a skill, Enter picks rather than sends, and never while an input method is composing. Esc or a space closes it. Three skeleton rows show while the skills are read, and one line says when there are none or the read failed; typing goes on as text.

At Send, `skillsNamedIn()` (contracts) finds each `/name` in the message, and `named()` keeps those the folder or you have, at most 5, in the order named. It reads each one's file again (up to 256 KB), drops the frontmatter, and takes the real paths of the file and of a skill's folder. A `/name` that's no skill is just words. The page holds Send with "Use up to 5 skills." when the message names more. Claude's own settings don't change: `settingSources: []`, hooks off and `strictMcpConfig` stay, so no hook, MCP server, plugin or allow rule comes with a skill, and its `allowed-tools` line is ignored.

## What Claude may read outside the worktree

`compose.ts` gives each start a `reads`: the real paths of the files you picked, each named command's own file, and each named skill's folder. The session saves it in `session.json` (`StoredSession.reads`), so every run reads it again, a follow-up's too. `tool-decision.ts` allows a read tool (`Read`, `Glob`, `Grep`) on a path that leads, once every symlink is followed, to one of those files or into one of those folders, and nothing else. An edit there, a file beside a picked one, or a folder whose name only starts the same (`review-2` beside `review`) stays refused as outside the worktree. A session saved before spec 022 has no `reads`, so nothing outside its worktree can be read. See `learn/local-security.md`.

## Limits

`ComposerStartSchema` takes a message of at most 10,000 characters, at most 100 tickets, 100 pull requests and 100 files, each once (Q5). A file's path starts with `/` or `~/`, has no control characters and is at most 4,096 characters. Skills count at Send: at most 5. The page checks the same limits before it sends (`composer-rules.ts` `addChip()` and `refusalFor()`). A full kind says why in place of its list, under the box, or to a screen reader from a row's +: "A session takes up to 100 tickets.", "A session takes up to 100 pull requests." or "Add up to 100 files.".

`POST /api/sessions` is still the one route with a 4 MiB body limit, set for 015's file text. With files sent as paths, the most the composer can send is about 140 KB. Fastify's own refusals, such as a 413 past the limit, are answered with their status rather than 500.

## On Home

- **The draft** lives in `features/home/store.ts` (zustand): the text, the chips in order, and the folder you picked. Home's rows, Ship on Tickets and the ticket dialog add chips to the same store (`addChip()`, and `dropChip()` for a row's + pressed again), so they wait there while you're on another page. Leaving Home keeps the draft, and a reload or a sent task clears it. Only the last folder a task started in is kept on this computer (`devhub.home`). The text box is react-hook-form, and its value is mirrored into the store, as 013's follow-up box does.
- **+ Add context** is `@devhub/ui`'s `ContextPicker`: one Radix Popover. Its first view is a menu of kinds (arrow keys move between them, and Esc returns focus to +). Picking a kind shows that kind's list in the same popup, with Back, a count, a search box that is the ARIA combobox, and a note on what Claude gets. The Jira and Pull request lists filter 009's search index in the browser, so typing never asks the server. A key or pull request link the list doesn't hold shows as "Add PROJ-9999". Each option leads with a checkbox (spec 025): ticking adds the chip after the others, never in place of one, unticking takes it out, and the list stays open for the next; closing it after a tick puts focus back in the box. The folder list leads with radios, since a session has one folder. The popup is compact (spec 026): `text-small` with 32 px rows, 288 px for the kinds and 320 px for a list, and a list stops at 460 px, or sooner when the window has less room. File from this computer reads "Any file. Claude reads it where it is." and opens the computer's file picker (above); focus returns to the box after you pick or cancel.
- **The chip strip** shows the first two chips in the order you added them, so the session's ticket leads, then `@devhub/ui`'s `ContextMore`: a chip-shaped button "+3" with the tooltip "Show all context". Its name starts with what it shows, "+3: Show all 5 items of context", so a voice command for "+3" finds it. The strip is one line at any width: a chip's label gives way with "…" before +N does, so the box never moves as chips come and go. A file chip shows its name, cut in the middle so the extension stays.
- **The context dialog** (`context-dialog.tsx`), opened by +N, is "Context for Claude" with the tabs Tickets, Pull requests and Files, each with its count, opening on the first that holds something. Each row has the mark, the key, number or file name, a sub line (a ticket's title and status, or a pull request's title, from the search index; a file's full path) and Remove. Removing moves focus to the next row's Remove, else to the tab, and a screen reader hears it. A kind with nothing in it has no tab (spec 025), so removing a tab's last row moves focus to the tab shown next, and removing the last chip closes the dialog with focus in the box. Done or Esc gives focus back to +N, or to the box when +N has gone.
- **Pasting** exactly one Jira key or one github.com pull request link adds its chip instead of the text (Q6). Any other paste is pasted as text.
- **The folder picker** follows Q7: your pick, else the first ticket's project's only folder, else the folder you last used, else the only folder. Several folders for the project read "Choose folder", and none at all reads "Add a folder", which opens Settings' folder dialog. **The agent picker** shows Claude's mark and the model and effort you picked, from the list Claude Code gives right now (`GET /api/agent/models`, spec 025). Both pickers open compact menus (`size="sm"`, spec 026). Both pickers appear together, once both have loaded, in a row that is there from the first paint (their own row under 640 px), so the box never grows or moves while Home loads (AC-1).
- **Ask or Build** (spec 026) is a `SegmentedControl` in the bar. Until you pick, a ticket chip means Build and anything else Ask; your pick stays for the draft and goes as the start's `mode`. An Ask session runs Claude Code read-only in the folder itself, with no worktree or branch (`learn/sessions-and-worktrees.md`).
- **The waiting banner** reads the session list and shows the `needs_you` session that has waited longest, with its first waiting call ("wants to run npm test") and how many more wait. `sessions.changed` keeps it live.
- **The quick starts** are Pick up a ticket (Tickets) and Review a pull request (the list's Pull requests tab, with focus on that tab). Fix failing checks and Draft a Slack reply wait for their own specs (Q12), as does Slack thread in the + menu.
- **New task** (⌥⌘N, or Ctrl+Alt+N elsewhere) opens Home with focus in the composer box (`shell/main-content.ts` `focusNewTask()`). Ship on Tickets and the ticket dialog's Add to composer go to Home the same way, through `useNewTask()`.

## Tests

`compose.test.ts` drives the real session service with real git repositories, Jira and GitHub faked by MSW, and the fake Claude SDK. It covers each refusal that makes nothing, and real starts with and without a ticket, with several tickets, with a picked file and with a named skill. `context-reader.test.ts` reads each chip through the real clients and connections, and files in a home folder of the test's own. `tool-decision.test.ts` checks a picked file by its own path, by `..` and through a symlink, an edit of it, the file beside it, and a skill's folder against one whose name starts the same. `skills-reader.test.ts`, `skills-service.test.ts` and `routes/skills.test.ts` use temporary folders as the repository and as `~`, so nothing reads the real `~/.claude`. `file-picker.test.ts` starts fake picker programs from a test search path, so no test opens a real dialog. `no-leaks.test.ts` runs a composer start through the real hub at trace level, and none of the message, file text, skill text, description, comment, diff or tokens reaches a log line or an event. `e2e/composer.spec.ts` runs on its own hub (4388), where the fake Claude Code writes the brief it got to `last-brief.txt` in its folder, so the spec reads back exactly what Claude saw. The hub's fake file picker in `e2e/fake-gh/` picks `e2e/fake-gh/picked/notes.md`, and the spec checks that the brief holds its path and not its text.
